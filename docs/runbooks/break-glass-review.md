# The quarterly review of break-glass uses

## Use this when

- Each quarter. The first is before production's v0, by C0.19.
- After any unexpected A1, A15 or tier-2 use ([A security alert](security-alerts.md)).

## Who does what

- The second reviewer runs the review, with `HearthSecurityReview` alone: read-only, and never the archive bucket. They needn't be technical.
- An Owner, with `HearthOrgAdmin` in management, shows which account and OU id is which before step 1, reads the RCP (step 6), and lists Identity Center's assignments and groups (step 8), each while the reviewer watches, since `HearthSecurityReview` can't name the organisation's accounts, or read its OUs, its policies or the directory. A3 alarms on that session, which the review expects.
- The person on call answers the reviewer's questions.
- The DPO reads the record, and confirms that each `case:` reference is a real request without naming anyone.
- The owner fixes what the review finds.
- A coding agent runs no step and sees no log line.

## Before you start

- `HearthSecurityReview` in management and in log-archive (a 4-hour session).
- An Owner with `HearthOrgAdmin`, `gh`, signed in, `jq` and a checkout of `main`, for the ids before step 1, the RCP in step 6, and step 8.
- The quarter's dates.
- Read access to the repository's merged PRs and its deployment history (each environment's deployments, which outlive the runs: [Deploying a release, and rolling one back](deploy-and-rollback.md)), `gh`, signed in, and `jq`.
- This repository's current name and two ids, which step 6's comparison reads once with `gh`, in a checkout of `main`, where gh fills `{owner}/{repo}` from the checkout's own remote (as the set-up runbook's step E.2 does), or, without a checkout, with `{owner}/{repo}` replaced by the owner and name in the address of the repository page whose merged PRs you read. It clears `GH_REPO` and `GH_HOST`, so no stray setting chooses the repository, and keeps the name GitHub prints, since GitHub answers a former name of a renamed or transferred repository with the repository it now names. Never take the name or ids from a row, an alert, a finding, the set-up's notes or `infra/.env.local`.
- The records of tier-2 changes the people who ran them kept for this review, the on-call notes of the quarter (containments, the GitHub roles' cut-off before an owner's rename, and the sessions the helper reported unwritten), and the set-up's notes.
- The ops mailbox's alert emails of the quarter, every ALARM and OK email from management's topic among them, kept until this review (steps 6 and 9); at the first review, every one since the confirmation of management's subscription (the set-up runbook's step K.5).

## Steps

First, which id is which. The queries and the buckets show accounts and OUs by id alone, and `HearthSecurityReview` can't list them by name, so while you watch, the Owner, with `HearthOrgAdmin` in management, shows each account's id by its name (`aws organizations list-accounts --query 'Accounts[].[Id,Name,State]' --output table`) and each OU's (`aws organizations list-roots --query 'Roots[].Id' --output text` prints the root, then `aws organizations list-organizational-units-for-parent --parent-id <the root> --query 'OrganizationalUnits[].[Id,Name]' --output table`). Expect exactly four accounts, management, log-archive, non-prod and prod, each `ACTIVE` (any other state, `SUSPENDED` or `PENDING_CLOSURE` say, is a finding), and three OUs under the root, `Security`, `Workloads` and `Recovery`; any other is a finding. Note which id is which for this review alone, off GitHub and out of the record, and destroy the note once the record is written: the Owner shows them again next quarter. Steps 1 to 6 read accounts, OUs and the root by this note.

1. In management, run each saved query on `/hearth/security/org-trail` over the quarter and a day either side of it, in UTC (Logs Insights' UTC setting, not local time), since the entries' folders are UTC days and `validate-logs` takes UTC times. Each row shows two times: `@timestamp`, when the copy received the event, which a query's range goes by, and `eventTime`, when the call was made. CloudTrail's guide says the copy's time is its delivery's, typically about 5 minutes after the call and not promised, so a call made in the quarter's last minutes can be stamped in the next quarter; and a session's close, or its continuation, can come an hour or so after it began. So take each row into the quarter it belongs to, never by its `@timestamp`: a break-glass assumption by the UTC time in its session's name (for a name not of the helper's form, by its `eventTime`), a put on the break-glass-log bucket by the session its key names, and any other row by its `eventTime`. A row that belongs to the quarter before or after is that quarter's record, read here only to reconcile this quarter's sessions with it (step 3).
   - `hearth/review/break-glass-sessions`: every break-glass assumption, with its session name, reason and source identity, refused ones included;
   - `hearth/review/admin-sessions`: every `HearthOrgAdmin` and `HearthSetUp` session, and every assumption of `OrganizationAccountAccessRole` or of a hearthbase role (`cdk-hearthbase-*`, what A15 alarms on);
   - `hearth/review/deploy-role-sessions`: the GitHub roles' sessions (`hearth-gh-deploy` and `hearth-gh-diff`), by account;
   - `hearth/review/root-and-assume-root`: any root activity and `AssumeRoot`;
   - `hearth/review/recovery-moves`: every account moved between OUs, with the ids of the OUs it left and joined, so the moves into and out of `Recovery`, and any other move, show by the ids the Owner showed (step 5 checks each);
   - `hearth/review/break-glass-entry-writes`: every put on the break-glass-log bucket, refused ones included, with its error code, the writing session (`userIdentity.arn`, the name after `assumed-role/hearth-break-glass/`) and its source identity beside the key, each key's puts together (step 3's writer check).
2. In log-archive, list the quarter's break-glass entries in every account's folder, and read each one. The log bucket is `hearth-break-glass-log-` followed by log-archive's account id, which `aws sts get-caller-identity --query Account --output text` prints in your log-archive session. `aws s3api list-objects-v2 --bucket <the log bucket> --prefix break-glass/ --delimiter / --query 'CommonPrefixes[].Prefix'` lists every account's folder, and `aws s3api list-objects-v2 --bucket <the log bucket> --prefix break-glass/<account>/<yyyy>/<mm>/` each folder's entries for a month. The folders are the UTC days the sessions began, so list the quarter's months in UTC, and the next quarter's first day (`--prefix break-glass/<account>/<yyyy>/<mm>/01/`), which holds the continuation entry of a session begun in this quarter's last hour. List them from the bucket, never only for the accounts the first query prints: the queries read the trail's CloudWatch copy, which shows nothing at all if it has stopped receiving the trail.
   - Each entry was written once: for each account's folder and month, `aws s3api list-object-versions --bucket <the log bucket> --prefix break-glass/<account>/<yyyy>/<mm>/` lists every version and delete marker. Each entry's key holds exactly one version and no delete marker; a key with more is a finding (the bucket's `EntriesNeverReplaced` should have refused the second put), and every version of it is read.
   - The accounts the trail delivers for are the trail bucket's folders, which come from the trail itself, not its copy: `aws organizations describe-organization --query Organization.Id --output text` prints the organisation's id, and `aws s3api list-objects-v2 --bucket <the trail bucket> --prefix AWSLogs/<the organisation's id>/ --delimiter / --query 'CommonPrefixes[].Prefix' --output text` lists one folder per account, named by its id. The trail bucket is `hearth-org-trail-` followed by log-archive's account id. Expect four, management, log-archive, non-prod and prod, whether or not anyone broke glass into them; one more or one fewer is a finding. Management's is the account in the trail's ARN, which `describe-trails` prints (below).
   - If the set-up's notes record a trail copy removed after Foundation's failed first deploy (with its event count and times), list the trail bucket (`hearth-org-trail-` and the same id) for those days, under `AWSLogs/`, and check it holds log files for those times; if it doesn't, it is a finding.
   - Validate the quarter's trail files against their signed digests, which shows a delivered file overwritten or deleted since. For each of the four accounts the trail bucket's folders name (above), management included, and in each of ap-southeast-1 and us-east-1, where the trail delivers the global services' events: `aws cloudtrail validate-logs --trail-arn <the trail> --account-id <the account> --start-time <the quarter's first day, as 2026-07-01T00:00:00Z> --region <the Region>`. `aws cloudtrail describe-trails --region ap-southeast-1 --query 'trailList[].TrailARN' --output text` prints the trail, `hearth-org-trail`. Each run ends by counting the digest and log files it found valid. An `AccessDenied` is a finding to raise, never a pass: the reviewer's reads, or `hearth-region`'s fence for them, have changed. Any `INVALID`, a missing file, or a gap it reports goes to [A suspected breach of personal data](breach.md), with `aws s3api list-object-versions --bucket <the trail bucket> --prefix <the key it names>` read for the keys it names. Record counts and results, never a key.
3. For each break-glass session the first query lists, and each session an entry names, reconcile three sources: the trail's assumption, the entries, and the merged PRs (and the deploy history). Every entry is keyed by its own session, the `session` it names, under the UTC day that session began. An entry keyed by a session the first query doesn't list over step 1's range is a finding: the copy missed the trail's event, and the Owner reads the trail's delivery to it at once (step 9). A session an entry names only in `continues` or `amends` may have begun in an earlier quarter: reconcile it with that quarter's record, not as a missed trail event. Check:
   - each session has one of these shapes, by the entries keyed by its name (`hearth-bg-` and its time), and any other shape is a finding:
     - a session the helper opened: an open entry and a close entry, the close written by the session or by its continuation (below). One with an open entry and no close is one whose close the helper reported unwritten, which the person noted, or that stopped unprompted past its hour: reconcile it from the trail;
     - a continuation: only its continuation entry, under its own day, whose `continues` names the session whose close it wrote, under the same reason and source identity;
     - an amend: only its amend entry (below);
     - no entry at all: a refused assumption (below); one the helper reported as "the role wasn't assumed" (AWS granted it but its reply never arrived); or one the helper stopped before its own entry was written, having reported the break-glass-log bucket's parameter unread, or its open entry, for a continuation its continuation entry, or for an amend its amend entry, unwritten. The person notes each of those with its time for this review ([Reaching production: the break-glass role](break-glass.md#when-it-stops));
   - each entry's `session` and `environment` match its key and the account its folder names, by the ids the Owner showed (non-prod's folder holds only `nonprod` entries, prod's only `prod`, log-archive's only `log-archive`);
   - the reason is a reference in its exact form, and holds no name;
   - the runbook named fits the reason;
   - a `case:` reference is a real request (the DPO confirms it);
   - an `lz:pr-` number is a merged PR whose diff matches what was deployed, but for the GitHub deploy subjects, which come from `infra/.env.local`, never from a PR: only a correction of GitHub's OIDC subject, a rename or transfer of the repository or a rename of its owner changes them ([the set-up runbook's step E](aws-account-set-up.md#e-githubs-oidc-subject-and-the-rest-of-the-configuration)), each citing the PR that records it, and step 6 reads them as they stand. Any other change in that deploy is a finding;
   - the close entry's modes and ids fit the runbook, and hold no name, number or address;
   - a session closed within two minutes of its hour, or after it, has its close written by a continuation, the role taken again under the same reason, unless the close wasn't written; one that stopped unprompted past its hour has no continuation and no close entry, so reconcile it from the trail. A session that began in the last hour before the quarter has its open and close in the previous quarter's folder and its continuation in this one, and one that began in this quarter's last hour has its continuation in the next quarter's first day (step 2). Before recording a missing assumption, entry or put for a session near either end of the quarter, look past that end;
   - a close entry with outcome `stopped` and no modes was written by the helper on its own, as it stopped: note what stopped it;
   - an amend entry, keyed by its own session under its own day, names the session it amends (`amends`, which may be an earlier quarter's), under that session's reason, and the amend's own session wrote nothing else;
   - a refused attempt with a reason that isn't a reference is a finding, since its tags stay in the trail;
   - each entry was written by the session its key names, from `hearth/review/break-glass-entry-writes`: the key's successful put came from the session after `assumed-role/hearth-break-glass/` in its `userIdentity.arn`, and the writer's source identity is the one on the `hearth/review/break-glass-sessions` row in the key's account whose `requestParameters.roleSessionName` equals that session name: match by name, never by source identity alone. Read the row whose `recipientAccountId` is the key's account, since log-archive's copy of another account's put may carry no session. Two writers are expected besides: a close written by the continuation session whose entry's `continues` names the key's session, with the same source identity, and an amend, `<the amend's own session>-amend-<the amended session's time>.json`, written by the amend's own session. Refused puts of a key that holds an entry have one expected shape: its successful put by one of those writers, followed within minutes, by `eventTime`, only by refused puts of it with `PreconditionFailed`, from that same session or one whose continuation entry `continues` the same session, under the same source identity. That is the AWS CLI retrying a put whose reply was lost, which then meets the stored entry, and, for a close, the helper's own unprompted second try, made with the same session's credentials (or, if the hour's last two minutes began in between, by a new session that writes its own continuation entry first). The helper then reported the entry unwritten, so the person's note of an unwritten entry may stand beside an entry that exists. The CLI retries an assumption the same way: when the reply to the helper's `assume-role` is lost, it sends the call again under the same name, and AWS grants it again. So two or three successful assumptions under one name in one account, within about three minutes of each other by `eventTime`, all with the same source identity and the same reason, are that retry: note it, it isn't a finding (the role's trust holds a session's source identity to the caller's own sign-in, so nobody else's session can match it). A name's time is the person's clock, read just before the helper assumes the role: normally seconds before the assumption's `eventTime`; up to about three minutes before it when the CLI retried; and off by as much as that clock is off AWS's, which can be up to about five minutes, since AWS refuses a signed request further off. Where the session wrote an open entry, its `at`, from the same clock, comes a few seconds after the name's time, or up to about three minutes after when the CLI retried. Note a larger gap with the person's account of it (a slow network, their machine's clock). Each of these is a finding for [A suspected breach of personal data](breach.md): any other writer; two sessions sharing a name (one session name on more than one successful assumption in one account, in `hearth/review/break-glass-sessions`) beyond the CLI's retry; a successful assumption whose name isn't of the helper's form, `hearth-bg-` and a UTC time, or whose time is further from its `eventTime` than those bounds with nothing to account for it; any other refused put of a key that already holds an entry (beyond step P.1's drill, which the set-up's notes record), an `AccessDenied` or one by another session or source identity among them; an entry with no put row. The role's trust doesn't constrain session names, so another session in the account can take an open session's name: the by-name match then finds two assumptions under it that aren't the CLI's retry, which is the finding itself. Record counts, never a key or a name.
   - each bastion run was placed as [*The bastion and a port forward*](break-glass.md#the-bastion-and-a-port-forward) places it, since `RunTask` has no IAM condition that refuses any other placement (TECH-SPEC T24 item 13) and a bastion start raises no alarm but its session's A1. The first query below lists the bastion runs over step 1's range, refused ones included; the second, over the copy's whole retention (731 days), the groups and subnets CloudFormation made. Expand each successful run's row: its `requestParameters.networkConfiguration.awsvpcConfiguration` must hold `assignPublicIp` `DISABLED`, exactly one security group, the `groupId` of the group described `Hearth <env> bastion task (C11-D31)` in the same account, and only the `subnetId`s of that stage's isolated CIDRs (`10.20.16.0/20` and `10.20.32.0/20` in non-prod, `10.30.16.0/20` and `10.30.32.0/20` in prod, `10.40.0.0/20` and `10.40.16.0/20` for the restore stage in prod's account), `<env>` being the stage its cluster, `hearth-<env>`, names. Any other group or subnet, a second group, a public address, or a successful run whose row shows no network configuration (the procedure always passes one) is a finding. If the second query finds no creation for that stage, because its network is older than the copy keeps, the run's placement can't be read from the copy: that is a finding too, which the owner settles with the person on call. Whether a `RunTask` record holds `requestParameters.networkConfiguration.awsvpcConfiguration`'s `subnets`, `securityGroups` and `assignPublicIp` as this check reads them is shown by the first real one, non-prod's first probe run by the deploy pipeline ([the set-up runbook's step R.7](aws-account-set-up.md#r-before-the-first-workload-deploy)): a field missing there is a PR to this check and its query. Note the ids for this review alone, as you noted the accounts', and record counts, never an id.

     ```
     fields @timestamp, eventTime, recipientAccountId, requestParameters.cluster, requestParameters.networkConfiguration.awsvpcConfiguration.assignPublicIp as publicIp, errorCode
     | filter eventSource = "ecs.amazonaws.com" and eventName = "RunTask" and requestParameters.taskDefinition like /bastion/
     | sort @timestamp asc
     ```

     ```
     fields @timestamp, recipientAccountId, eventName, requestParameters.groupDescription, requestParameters.cidrBlock, responseElements.groupId, responseElements.subnet.subnetId
     | filter eventSource = "ec2.amazonaws.com" and not ispresent(errorCode) and ((eventName = "CreateSecurityGroup" and requestParameters.groupDescription like /bastion task/) or eventName = "CreateSubnet")

     ```

4. Each hearthbase assumption (A15) the second query lists has an `lz:` reason and a merged PR, a reviewed Foundation deploy (with its A3; the RCP's subjects come from `infra/.env.local` too, and step 6 reads them as they stand), the set-up's first deploys, or a recorded tier-2 change.
5. Each `HearthOrgAdmin` session and each assumption of `OrganizationAccountAccessRole` has a reason: a reviewed Foundation deploy, a tier-2 change, the set-up, or a containment or the GitHub roles' cut-off before an owner's rename (the on-call notes). A `HearthOrgAdmin` session may also be an Owner's read or change that another runbook asks for, matched with what records it: an alert's triage (noted with the alert), the quarterly read-backs (step 9), an Identity Center change step 8 matches, the read of a deploy's source identity for TECH-SPEC T24 item 4 ([Reaching production: the break-glass role](break-glass.md)), or a review's own reads, this one's or an earlier one's that ran into this quarter. A `HearthSetUp` session after the set-up is a finding. Each move `hearth/review/recovery-moves` lists is a recorded tier-2 change, the account moved from its own OU (log-archive's `Security`, a workload account's `Workloads`) into `Recovery` and back into that same OU, or one of the set-up's moves, each account from the root into its own OU; any other move is a finding, even one undone since, and so is a refused one that no recorded change explains.
6. Each deploy-role session matches the deploy history. Each `hearth-gh-deploy` or `hearth-gh-diff` session that `hearth/review/deploy-role-sessions` lists (step 1) is named `gha-<run id>-<attempt>`, and the run id is in the `log_url` of the statuses of that environment's deployments (GitHub's own per-job ones and the pipeline's records), after `actions/runs/`; the deployments outlive the runs' 14-day retention. For each environment (`nonprod`, `prod-plan` and `prod`), `gh api --paginate 'repos/{owner}/{repo}/deployments?environment=<env>&per_page=100' --jq '.[] | [.id, .created_at, .task] | @tsv'` lists its deployments, and `gh api 'repos/{owner}/{repo}/deployments/<id>/statuses' --jq '.[].log_url'` names each one's run. A session no deployment names is a finding. Then check whom GitHub's deploy roles and the RCP let in. This catches a mistake or an unreviewed change in the deploy subjects, which come from `infra/.env.local` rather than a PR, and any drift from the subjects the code renders. It doesn't try to stop an Owner hiding a change on purpose. An Owner writes the trusts through OAAR (at the set-up or under tier 2) and the RCP with `HearthSetUp` or `HearthOrgAdmin`, and could also stop the trail. The person on call's `lz:pr-` deploy writes the trusts too, but can't stop the trail, which is management's: its writes are CloudFormation's, under a merged PR and a session step 3 reconciles. Every such write after the set-up runbook's step K.5 raises A5 or A6 (i) at the time, triaged then; the set-up's own writes are read by its *Check it worked* (TECH-SPEC T24 item 29). The analyzer reports only principals outside the organisation, so a principal inside it added to a trust shows in no read. Only OAAR can add one by hand (`ProtectRoles`): the set-up's steps never do, and a tier-2 change that writes a GitHub trust records that it left it as the code renders it ([Reaching production: the break-glass role](break-glass.md#tier-2)). A deploy adds one only from code other than its PR's, which its fresh checkout of `main` at the merged PR and its read of the whole diff stop (the same runbook's *A Baseline deploy under `lz:pr-N`*).

   Four places hold the subjects: non-prod's `hearth-gh-deploy`, for GitHub's `nonprod` environment, prod's `hearth-gh-deploy`, for `prod`, and prod's `hearth-gh-diff`, for `prod-plan` (`infra/src/baseline/github-oidc.ts`); and the RCP's `WebIdentityOnlyDeploySubjects`, which lists all three (`infra/src/foundation/guardrails.ts`). Each must be what the code renders (`SUBJECT_SHAPE` in `infra/src/config/env.ts`): `repo:<R>:environment:<the environment>:job_workflow_ref:<R>/.github/workflows/deploy.yml@refs/heads/main`, each `<R>` this repository as GitHub names it now, as `owner/name` or as `owner@<owner id>/name@<repository id>`. Either form names this repository alone, and a form GitHub doesn't send only refuses deploys. A role's environment comes from its account and its name, never from its subject.

   **Set up the comparison** in your log-archive session, with the account ids the Owner showed before step 1, and the Owner in their management session, each shell after `unset HISTFILE`, so neither keeps the line naming the accounts once the note is destroyed. Its first line reads this repository's name and ids, as *Before you start* says, and prints them: both shells must print the same line, the repository's whose merged PRs you read, and you run no read until they do. Where `gh` isn't signed in (a break-glass shell), set `REPO='<the line your own shell printed>'` in place of the first line.

   ```sh
   REPO="$(env -u GH_REPO -u GH_HOST gh api 'repos/{owner}/{repo}' --jq '[.full_name, "\(.owner.login)@\(.owner.id)/\(.name)@\(.id)"]')"; jq -c . <<<"$REPO"
   NONPROD='<the non-prod account id>' PROD='<the prod account id>'
   judge() { jq -r --argjson r "$REPO" --arg nonprod "$NONPROD" --arg prod "$PROD" 'def gh: "token.actions.githubusercontent.com";
     def ok($e): $e != null and IN([$r[] as $a | $r[] as $b | "repo:\($a):environment:\($e):job_workflow_ref:\($b)/.github/workflows/deploy.yml@refs/heads/main"][]);
     def line: .resourceOwnerAccount as $a | (.resource | sub("^.*:role/"; "")) as $n
       | {"\($nonprod) hearth-gh-deploy": "nonprod", "\($prod) hearth-gh-deploy": "prod", "\($prod) hearth-gh-diff": "prod-plan"}["\($a) \($n)"] as $e
       | [.analyzedAt, $a, $n, if .principal == {Federated: (["arn", "aws", "iam", "", $a, "oidc-provider/" + gh] | join(":"))}
           and .condition == {(gh + ":aud"): "sts.amazonaws.com", (gh + ":sub"): .condition[gh + ":sub"]} and (.condition[gh + ":sub"] | ok($e))
         then "expected" else "FINDING" end] | @tsv; '"$1"; }
   ```

   1. **The trusts as they stand**, in your log-archive session, from the organisation analyzer, which reads every role in every account: each active finding on a `hearth-gh-` role or naming GitHub's provider, with when the analyzer last read the role (`analyzedAt`). A finding gives each condition's key and value but not its operator, so this read can't tell `StringEquals` from another: the code renders `StringEquals` alone (IAC-10 holds it), and every write to a trust after the set-up raises A6 (i) at the time and is matched in the third read.

   3. **The quarter's changes**, with this query on `/hearth/security/org-trail` in your management session, over the quarter and a day either side (step 1; at the first review, from the set-up's first day): every call that set or removed a GitHub role's trust, and every change to the organisation's policies, refused ones included.
