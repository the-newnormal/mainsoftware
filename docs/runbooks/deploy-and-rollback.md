# Deploying a release, and rolling one back

## Use this when

- A merge to `main` is deploying: non-prod by itself, then prod once its reviewer approves.
- A release must be rolled back, in non-prod or in prod.
- The pipeline rolled a release back: a red run, or an A14 email ([A security alert](security-alerts.md)).
- A deploy job was cancelled or timed out, a stack is stuck, or a migration failed.
- A failed job is to be re-run.
- The pipeline must be paused, and later resumed: around every run of the Owner bootstrap script ([Setting up the organisation and its first Owner](first-owner-set-up.md), [Twilio withdrawn, and no DPO signed in](twilio-withdrawn.md)) and around the set-up runbook's cut-off of the GitHub roles ([Setting up the AWS organisation and its accounts](aws-account-set-up.md), step E.2).
- The commit the database was migrated by is needed.
- The rollback rehearsal is due, or the restore stage goes up or down.
- A7 emails about a prod run.
- The upkeep calendar (*Upkeep*, below).

## Who does what

- Whoever merges a PR to `main` starts non-prod's deploy, Claude among them while non-prod holds synthetic data. From C0.12's change that makes non-prod hold real data, `.github/environments/nonprod.json` asks for a reviewer and non-prod's deploy waits for the owner too (C11-Q05). A merge whose commit message holds a skip instruction (`[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or `[actions skip]`, or a `skip-checks: true` trailer, which a squash merge's default message can carry from the pull request's title, description or commits) starts no run, of the deploy workflow or of `main`'s CI, so after a merge the person who merged it (the owner, when Claude merged it) checks that a deploy run started; if none did, the owner dispatches `deploy` to `nonprod`, and prod waits for the next merge (`prod-gate` finds no `main` CI on that commit and fails). A merge the gate would refuse, its head shared or its checks not green (*A release, from merge to prod*, step 1), has that dispatch refused the same way. And until `deploy.yml` is under GitHub's 500 KB limit for a workflow file, which it is over as committed (TECH-SPEC T24 item 20, the owner's decision on its structure), no merge or dispatch starts it at all.
- The owner approves prod's deploys and rollbacks and the restore stage, only in GitHub's web UI, and dispatches rollbacks, drills, restores and a deploy that a merge didn't start there: Actions, then the deploy workflow, then Run workflow.
- A repo admin pauses and resumes the workflow, applies the environments with `scripts/protect-environments.sh apply` and sets their secrets ([Setting up the AWS organisation and its accounts](aws-account-set-up.md), step E.4).
- The person on call handles A14 and A7 and, while GitHub is down, the incident rollback under break-glass ([Reaching production: the break-glass role](break-glass.md#an-incident-rollback-to-an-earlier-revision)).
- The second reviewer reconciles the deploy roles' sessions with the deployments each quarter ([The quarterly review of break-glass uses](break-glass-review.md), step 6).
- Claude, like any coding agent, never approves, rejects, dispatches, re-runs or cancels a run, never pauses or resumes the workflow, never writes a deployment, and never edits an environment, its reviewers or its secrets, by any route: a terminal, a GitHub connector or a browser.

## Before you start

- A GitHub login that can take the step: the owner's to approve and dispatch, a repo admin's to pause, never one a Claude Code session can use (C11-D57).
- For a `gh` line: `gh`, signed in, and `jq`, in a terminal outside any Claude Code session, in a checkout of `main` kept current (a plain `git pull` on its `main` branch, never a pull given `origin main`, which takes a tag named `main` over the branch and would merge that tag's commit, a branch's code, into the checkout; anyone who can push a branch can push such a tag), where `gh` fills `{owner}/{repo}` from the checkout's own remote, with `GH_REPO` and `GH_HOST` unset. A line that writes (disabling or enabling the workflow, cancelling a run) needs a repo admin's login, which lives only with the separate operating-system user the set-up runbook keeps for its shells ([Setting up the AWS organisation and its accounts](aws-account-set-up.md#before-you-start)), where no Claude Code session runs: `gh` keeps its login in the operating-system user's own credential store, which every process of that user can read. The other lines only read. For a `node infra/scripts/deploy/…` line: Node 24.12 or later (`node --version` prints `v24.12` or a later 24, as the root `package.json` asks) in the same checkout; on a Node 24 before 24.2 each script refuses with one line holding `Node 24.2 or later is needed (import.meta.main)`, floors-check's own, since each loads it, and exits 1, having decided nothing: take a newer Node and run it again. The scripts load no npm package, so the checkout needs no install.
- A release is `<commit>:<digest>`: the commit on `main` it was built from, and its image's digest. The release a run deploys is the gate's `commit` with, for a deploy, the build's digest (`build: hearth-server@<digest>` in the build job's summary), or else the gate's `digest` (its summary, *The plan*). The deploy jobs' lines name it too, through a filter that blanks an account id (a run of twelve digits with no digit or lowercase hex letter beside it) and leaves a commit or digest whole.
- The records are GitHub deployments in the environment `nonprod` or `prod`, which the repository's Deployments page lists by environment. The pipeline writes three kinds, by task: `hearth-release` (a release that passed its smoke, or the release the pipeline rolled back to), `hearth-migrated` (the commit a migrate step applied, from C0.12) and `hearth-restore` (the restore stage brought up or down). GitHub adds one of its own for each job that names an environment, which names no release. An environment's release records, newest written first: `gh api 'repos/{owner}/{repo}/deployments?environment=<env>&task=hearth-release&per_page=20' --jq '.[] | [.id, .payload.kind, .payload.commit, .payload.digest] | @tsv'`. The pipeline orders them by the api service's task definition revision instead, since a record job runs outside the deploy group and a later run's record can land first. Read them as data: anything with Deployments write can add one, and the pipeline's own readers ignore any whose payload fails validation, each named by its id in the gate's and `prod-gate`'s summaries (`history: ignored hearth-release record <id> in <env>: its payload fails validation`).

## Steps

### What a dispatch can ask for

A dispatch runs on `main` (Actions, then the deploy workflow, then Run workflow), with four inputs. A deploy always deploys `main`'s head; an older release goes back only as a rollback. The gate refuses every other combination, and any run a bot starts or re-runs (`bot-actor`); every job after the gate also skips itself by its own bot test on a bot's re-run, so a bot's re-run deploys nothing, though a re-run gate still runs its read-only checks before it refuses.

| To | target | mode | release | restore |
|---|---|---|---|---|
| Deploy to non-prod alone | `nonprod` | `deploy` | empty | `none` |
| Deploy to non-prod, then prod | `prod` | `deploy` | empty | `none` |
| Roll an environment back | `nonprod` or `prod` | `rollback` | the release's commit | `none` |
| Run a drill | `nonprod` | `drill-break` or `drill-smoke` | empty | `none` |
| Bring the restore stage up or down | `restore` | `deploy` | empty | `up` or `down` |

### A release, from merge to prod

A push to `main` runs the deploy workflow as `mode=deploy`, `target=prod`. Each job's summary says what it did. In order:

1. `gate` checks who started the run and where; that the commit is its merged PR's tree, with that PR's `check` and `migrations` green; that `main`'s ruleset holds its deletion, non-fast-forward and pull request rules and the two required checks (`gate: main's ruleset isn't live` otherwise; it reads nothing else of the ruleset, the approval count, the merge methods and thread resolution among them) and that the environments are live as written (a `protect-environments: <name> <field> differs` line names what isn't: the set-up runbook's step E.4 puts an environment right, a `name` line included, which `apply` alone can't, and its step E.1 an `oidc` line); the floors, and that each environment it deploys runs (by its newest release record) a release at or after the expansion of every floor at the commit whose migration it lacks (`history: refused expansion-not-deployed: …`, *Floors*); and that `DOMAINS` holds no placeholder. *The plan* lists the mode, the target, the commit, each environment's current release and the release each automatic rollback would go back to. A refusal is one line, `history: refused <code>: <why>`. The PR's checks are read from the newest `ci.yml` run on its head commit from the PR's own head repository (by id) and branch whose latest attempt started while the PR was open, from its creation to its merge, so a run re-run after the merge isn't counted, and with no other the PR's checks read as missing (`history: refused pr-checks-failed`). `pr-checks-failed` while the PR shows green, its own run not re-run since the merge, means another run of `ci.yml` at that head, started while the PR was open, was chosen: a repo admin, never Claude, deletes that stray run in the web UI (its page, then Delete workflow run), and the deploy is dispatched again (`deploy` to `prod`). GitHub ties no run to the PR that started it, so the gate also refuses a PR when another PR from its head branch, into any base and in any state, was open at any moment while it was, or has its head commit, or when that branch's PRs can't all be read (`history: refused pr-head-shared: another pull request from the merged one's head branch was open while it was, or has its head commit, or that branch's pull requests couldn't all be read, and GitHub ties no ci.yml run to the pull request that started it, so the merged one's own checks can't be told apart: the next merge whose head no other pull request shares deploys what this one brought`): such runs can't be told apart, whichever passed. Nothing about a commit refused either way can be re-run into a deploy, and while it is `main`'s head every dispatch of `deploy`, to either target, is refused the same way; the next merge whose head no other PR shares, and whose own run passed while it was open, deploys what the refused one brought. A branch carries one open PR: to change a PR's base, edit it rather than open another beside it (`ci.yml` runs again on the edit, testing the merge into the new base, which the gate then reads; a base change started no run before, so the gate read checks of the merge into the old one). A PR from a branch name an earlier PR used, which closed before it opened, at another commit, isn't refused: Renovate reuses its branch names (the CDK group's is always `renovate/cdk`), and its merges deploy as any other. One case stays that the gate can't tell apart, as GitHub's own required checks, which read a commit's checks by its sha, can't either: a re-run, while the PR is open, of a closed PR's earlier run at the same commit, which needs the branch pushed back to that commit.
2. `build` makes the server image on ARM and checks it as CI does; `synth` synthesises the release's cloud assembly, and `synth-previous-nonprod` and `synth-previous-prod` each environment's previous release's, each on a runner of its own. None holds a credential. Each runs repository code (the release's, or an earlier release's), which can write that job's own summary and annotations in any words, a heading and a code block that look like the diff or *The plan* among them, and GitHub shows the jobs' summaries in the order they finished: read the diff and *The plan* only where steps 4 and 6 say.
3. `nonprod` first lists the build's image archive and unpacks it itself, before it takes any credential (an `image-check:` line, such as `image-check: the image's archive holds a member buildx's OCI export never writes`, stops the run there: the build made an archive the pipeline doesn't push, so tell the person on call rather than re-run it); then it checks what runs and that no image in ECR is of a later commit than the run's (`aws-check: deploy passed: Hearth-nonprod-Services is <status> and runs <release>`), pushes the image from the folder it unpacked, deploys Platform, Data and Tasks, migrates (from C0.12), deploys Services, probes, and reads back what runs (`read-back: Hearth-nonprod-Services runs <release>`). `smoke-nonprod` prints one line a check, `SMK-0n pass` or `SMK-0n fail <reason>`, and `record-nonprod` writes the release record and shows it in its summary. A record job runs only once its deploy job has succeeded or failed, in non-prod as in prod, so a run whose deploy job never ran (a failed `synth-previous-nonprod`, say, or a job replaced in its concurrency group) shows no record failure beside the real one. C0.11's Done asks for under 20 minutes from the merge to the green smoke; the first runs measure it. A red non-prod never stages prod.
4. `prod-plan` diffs prod's deployed templates against the release through `hearth-gh-diff`, a role that reads the prod and restore stacks' templates, status and resources and nothing else, into its summary, *What prod's deploy changes*, as one code block, cut at 200 KB with a line saying so (the job's log holds it whole). Everything inside the code block is the diff: no line of it is the page's own text. The only lines after the block are the pipeline's: the 200 KB cut note, which means the rest of the diff is in the job's log, to read there before approving, and a failed diff's note, which fails the job. Read it only in `prod-plan`'s own summary, the box on the run's summary page headed with that job's name, or in its *Diff* step's log: a box headed `build`, `synth` or `synth-previous-…` is repository code's, and can copy this heading and a block of its own. The diff names every stack the approval deploys: the deploy-workflow guard holds each of prod's deploy lines to the stacks its mode's diff names, as literal sets of its own (every stack for a deploy or a restore `up`, Tasks and Services for a rollback, one restore stack at a time for `down`). Two warnings are expected: the session "could not be used to assume" the lookup role, and "Lookup role … was not assumed. Proceeding with default credentials." A normal release changes the Tasks and Services stacks' task definitions (the image's digest) and the `Release` output. A parameter's `Default` in the diff isn't the value it deploys with. Every workload parameter is SSM-typed: its `Default` names an entry in the parameter store, and the deploy takes whatever that entry holds as the stack deploys (every deploy passes `--no-previous-parameters`, so no earlier value is kept). The asset check holds every `Default` to one of the workload's own entries and refuses `Conditions`, `Mappings` and any brace a string could join into a `{{resolve:…}}` reference, but what an entry holds is never in the diff: a stack earlier in the same run can write it, and an `AWS::SSM::Parameter` a release adds shows as one line with no value. Another stack's output is never in the diff either: `Fn::ImportValue` and `Fn::GetStackOutput` read one as the stack deploys (`Fn::GetStackOutput` through a role in another account, the diff showing only the reference, its account `***`), so the asset check refuses both, every intrinsic function the workload's templates don't write, and an output that exports a value. The asset check refuses a parameter in a role's statement, condition or trust; reject a release that puts one in any other IAM statement or condition (prod's templates have one there today, the organisation's id in the endpoint policies, which the asset check holds exactly), or that adds an entry or changes what one holds without its PR showing the value. Anything else is a change the merged PR made, or one made by an earlier PR, merged since the release prod runs, whose prod deploy was rejected or failed: match it with those PRs before approving. The asset check holds every template to the resource types the workload's stacks write, so no IAM policy, user, group or key reaches this diff, and every role to the keys the workload writes, the account's own boundary and inline policies of distinct names (IAM keeps one document to a name, while this diff would show both), so no role attaches a managed policy by its ARN, which the diff would list in an *IAM Policy Changes* table by that ARN alone and never print what it grants: if such a table appears, reject the run. An added resource of those types shows as one line, its type, path and name, never its properties (a role it names, say): match each added resource with the PR that adds it, and read its properties in that PR's code. The diff names every resource by its construct path, never its name: an added role's line doesn't show its `RoleName`, and the *IAM Statement Changes* and *Security Group Changes* tables name each grant's principal (`AWS:${Platform/Roles/ApiTask}`) and each rule's groups by path alone. The asset check ties each principal's and group's path to the resource it labels (its logical id, and a role's name, a group's parameter or user, a task definition's family and a service's name), so a grant under a role's path is that role's; and it refuses a role that names anything by a reference but the account's id, the template's VPC and that VPC's default security group, so every other resource a grant reaches is named in the table by its ARN, never by a path or a parameter's label (a parameter labelled `Platform/Network/Vpc` prints as the VPC does); a template holds one VPC at most, at the synth's path, and no two resources the diff prints under one label, so `Platform/Network/Vpc` in a grant or condition is the workload's own VPC (a second VPC at `Platform/Network/Vpc`, beside the workload's at `Platform/Network/Vpc/Resource`, printed as it does); and a template's rules and parameters take CDK's own ids alone, which no resource takes, nor an output's, so a resource line marked `[-]` and the grants it removes print under the removed resource's own path (the CLI labels a removed resource whose id the release reuses for a rule or a parameter by that one's logical id entry, so a removed api task role printed as the bastion's, the rule itself never shown). The asset check also holds every resource's properties to the keys and forms the workload's synth writes for its type, every ARN in a template to the account's own, in `ap-southeast-1` or IAM's, every parameter and Hearth name to the stack's own stage, a security group's inline egress to CDK's own disallow-all rule, and what a task definition, service, security group rule, VPC endpoint, load balancer, listener, record, parameter or role names or opens to the synth's shape (a task's roles, image, log group and secret, and its one container, named `server`, a service's network and target groups, and the Services stack's three services, each on its own family's definition, an endpoint's policy, a role's trust), so an added resource's unprinted properties can't reach another account, another stage or another target, and no release renames, adds or drops what the pipeline's checks and rollbacks read by name; a container's environment, command and health check stay the release's own, as the image is, so read an added or changed one in its PR. It also holds every metadata entry in the assembly to the types the synth writes and the CLI's notes, so no stack tags reach CloudFormation outside a template (an older CLI applied them to every resource of the stack, which no diff shows). Before it diffs, `prod-plan` reads each stack of the stage it diffs, its status and when it last changed (a `plan-basis:` line refuses one still moving: wait for it to settle, then re-run `prod-plan`), and `prod` later deploys only while every stack reads the same (step 6). The one custom resource, CDK's default security group handler in the Platform stack, answers at deploy time with values the diff never shows; the asset check holds it to CDK's shape: its own function, run from a zip in the staging bucket at a key of 64 hex digits and `.zip`, with CDK's properties and no others (no layer, environment or network of its own), run as its own unnamed role, trusted by Lambda alone, and nothing in its template reading its answer. (The flow log delivers as its own unnamed role too, trusted by VPC flow logs alone, and every named role, a task's or an execution role, is trusted by ECS tasks alone.) The zip's bytes are the release's own, as the image is, and no check reads them: the key is held to its shape, never to the bytes, and the CLI uploads nothing to a key the bucket already holds, so the first release to upload a key decides what every later one naming it runs. The handler's code can therefore do only what its own role grants, which the diff's *IAM Statement Changes* table shows, under that role's path (`AWS:${Platform/Custom::VpcRestrictDefaultSGCustomResourceProvider/Role}`), whenever that grant is added or changed: a grant under any other role's path is never the handler's. So reject a release whose diff adds a custom resource, a function or a reference to either, or changes any of that function's properties but its code's key and its runtime (a new release of aws-cdk-lib changes the key and can move the runtime to a later `nodejs<n>.x`: match either change with the PR that bumps aws-cdk-lib, which accepts that release's own bytes under the new key, and reject any other, its description, memory, timeout, handler or role among them). The one exception is a diff that creates the Platform stack, every resource of it added, its VPC among them: prod's first deploy (*The plan*'s `first_prod` reads `true`), and a restore `up` that creates `Hearth-restore-Platform` (the first, or one after tier 2 removed it). It adds that custom resource, its handler's `AWS::Lambda::Function` and the handler's role, in the Platform stack alone, which the asset check holds to CDK's shape: accept those three, matched with C0.11 PR 3, which added them, and see all three lines (`[+] Custom::VpcRestrictDefaultSG Platform/Network/Vpc/RestrictDefaultSecurityGroupCustomResource`, `[+] AWS::Lambda::Function Platform/Custom::VpcRestrictDefaultSGCustomResourceProvider/Handler` and `[+] AWS::IAM::Role Platform/Custom::VpcRestrictDefaultSGCustomResourceProvider/Role`), the handler's `ec2` grants and its Lambda trust in the IAM table under that role's path alone, since an added function's line never shows which role it runs as (the asset check refuses it running as any role but its own), and reject a second custom resource or function, one in another stack, or a reference to either from anything but each other. The diff masks every 12-digit number, so an ARN whose account reads `***` there may be another account's: read any added or changed ARN whole in its PR. When prod has a previous release, the same summary then holds *What prod's automatic rollback changes*: the Tasks and Services of the assembly `rollback-prod` would deploy if prod's smoke fails, the previous release rebuilt from its own code, against the templates prod's Tasks and Services stacks hold now. *The plan* names that release as `previous_prod_commit`; when it names one for a deploy and this section is missing, reject the run (`prod-plan` stops at *The artifacts' names* itself when `synth-previous-prod` named no assembly, so a summary without the section is not one this runbook describes). It should show no change (the same two warnings aside), but for two cases. A prod run whose deploy finished but whose smoke or record job was still running when `prod-gate` read the records (shown as still running on the runs list) leaves its release live with no record yet, and the diff shows its Tasks and Services going back to the previous release: if its record lands before this run's `prod` starts, `prod` refuses (*On approving*); if you approve and it lands after, this run's automatic rollback, should its smoke fail, goes past that release back to `previous_prod_commit`. So wait for that run to end, reject this one, and re-run all its jobs or dispatch afresh (*On approving*). (A release recorded before `prod-gate` read the records stops this run there, `history: refused record-changed`, before any approval.) And a prod run since prod's newest release record that got past its Tasks deploy and wrote no record leaves its own templates there: a deploy job that failed (at its migrate, or at its Services deploy, which CloudFormation rolls back alone), was cancelled or timed out; a run whose rollback was rejected, failed, skipped or rolled nothing back; or a dispatched rollback whose smoke failed. The Tasks stack holds that run's templates, and so does the Services stack where its release stayed live, until a prod deploy or rollback succeeds. The diff then shows those stacks going back to the previous release, which is what the rollback would do: each change one that such a run's own diff made (its *What prod's deploy changes*, or a dispatched rollback's *What prod's rollback changes*, in its own `prod-plan` summary), image digests and, where its release stayed live, `Release` among them, now going back. Find such runs on the deploy workflow's runs list, among those that failed or were cancelled since the run that wrote prod's newest release record, and approve only when every change matches one of theirs. Any other change is something the rebuilt release would deploy that isn't running now: reject the run, and find out why the rebuild differs before prod deploys again.
5. `prod-gate` waits up to 30 minutes for `main`'s own CI on the commit (`ci.yml`'s `check` and `migrations`), then checks that the commit descends from prod's current release, read afresh, that this release is at or after every floor's expansion it needs (`expansion-not-deployed` again), that prod gets the very image non-prod deployed, and that prod's newest release record is still the one the gate read (`record-changed`: another run's release recorded since would otherwise stay outside this run's automatic rollback and its diff, *On approving*).
6. `prod` waits for its reviewer. Approve only on the run's page in the web UI (Review deployments, then `prod`, then Approve and deploy), after reading the diff (in `prod-plan`'s own summary, step 4) and *The plan* (in the gate's own summary, the box headed `gate`). After the approval it checks that `prod-plan` ran in the same attempt of the run and that prod's newest release record is still the one `prod-gate` read, before it takes any credential; then, once it holds its credentials and before it checks, pushes or deploys anything, that every stack of the stage reads as `prod-plan` read it before its diff (`plan-basis: Hearth-<stage> is as prod-plan diffed it`), so a rollback or deploy another run made since, recorded or not, stops it (`plan-basis: Hearth-<stage> changed since prod-plan diffed it`); then it deploys as `nonprod` did. `smoke-prod` and `record-prod` follow.

On approving:

- An older run still waiting for its approval is either replaced by a newer run's or holds `deploy-prod` and blocks it (the first runs show which, TECH-SPEC T24 item 20; *Afterwards*): reject it. Rejecting starts no rollback job.
- Another run's `prod`, `rollback-prod` or dispatched rollback that changed prod after this run's `prod-plan` diffed it, finished or still running, makes this run's `prod` refuse (`plan-basis: … changed since prod-plan diffed it`) before anything moves, and a release another run recorded after this run's gate read the records makes `prod-gate` refuse (`history: refused record-changed`) before the approval. Once that run has ended, re-run all of this run's jobs while its commit is still `main`'s head (`git fetch origin +refs/heads/main:refs/remotes/origin/main && git show-ref --verify --hash refs/remotes/origin/main`), or dispatch `deploy` to `prod` afresh, then read the fresh diff and approve again. Never re-run `prod-plan` alone after another run's `prod` changed prod: it keeps the gate's read of the records, and with it the release this run's automatic rollback would go back to, so its `prod-gate` refuses again, or its rollback diff shows that run's release going.
- A run's artifacts last 14 days: an approval given later fails at its download, and a dispatch of `deploy` to `prod` replaces it.
- *The plan*'s `rollback_<env>` reads `false` while it names a `previous_<env>_commit`: the release adds a floor (or the previous release is below one), so no automatic rollback will run, and a rollback across the floor is refused (`floor-crossed`). The gate has checked that the environment runs the floor's expansion, so the migrate step contracts nothing under a release that still reads what it removes; a failure is fixed forward.
- **Prod's first approval** waits until the set-up runbook's step R.7 proofs and non-prod's rehearsal (*The rehearsal*, whose `drill-break` gives the A14 email) are done (TECH-SPEC T24 item 5). Leave the first run's prod approval waiting meanwhile, or reject it and dispatch `deploy` to `prod` afterwards. In its diff each stack no earlier run created shows every resource as added, the Platform stack's custom resource, handler function and role among them (step 4's one exception): match each with C0.11 PR 3, which added the workload's stacks, or a PR merged since.
- Every approved prod run raises one assured A7 episode, since each changes stacks in prod's account (a deploy or a rollback at least the Tasks and Services stacks, whose task definitions name another image): match it with the run ([A security alert](security-alerts.md)).

### When the pipeline rolled back

- A deploy job that failed once its Services deploy began, or a failed smoke: ECS's circuit breaker and CloudFormation's stack rollback act first (A14 emails when the breaker fires). Then `rollback-<env>` (unless it shows as skipped, below) checks that this run's release is what runs, that the release this run's deploy replaced is the previous release or a later one (a rebuild or a later commit), and that no image in ECR is of a later commit than the run's. If all three hold, it deploys the previous release (*The plan*'s `previous_<env>_commit`: the newest release record when the gate read them) from that release's own assembly, probes and reads back; `resmoke-<env>` judges it, and `record-<env>` writes a `pipeline-rollback` record. Prod's rollback job waits for the reviewer again: it deploys the Tasks and Services stacks of *The plan*'s `previous_prod_commit`, from the very assembly `prod-plan` diffed, so before approving read that and the run's *What prod's automatic rollback changes* (which shows no change, or only what step 4's two cases explain), with *What prod's deploy changes*, whose Tasks and Services changes it takes back, each in its own job's summary (the gate's and `prod-plan`'s), as steps 4 and 6 say. The run ends red either way (`record: the release's own smoke didn't pass, so the run ends red`).
- What next: a forward fix by PR, or a manual rollback further back (*A manual rollback*).
- On a first deploy (*The plan*'s `first_<env>` reads `true`) there is no earlier release to go back to, and a dispatched rollback is refused (`no-release`). Fix forward by PR, or, for a failure that may not recur, dispatch `deploy` to the same target, which deploys `main`'s head again (TECH-SPEC T24 item 20); a Tasks or Services stack a failed create left is handled as *A stack that is stuck* says.
- When the rollback job rolled nothing back (`rolled=false`) because `aws-check: auto: this run's release isn't what runs …`, nothing of this run is live. Either ECS's circuit breaker and CloudFormation's stack rollback already put back the release this run's deploy replaced, which is the usual end of a failed Services deploy and of a forward deploy's A14 email (the deploy job's `aws-check: deploy passed: … runs <release>` line names that release), or another run has deployed since, and its own smoke and rollback judge it. Roll nothing back for this run: fix forward by PR. In prod, unless another run has deployed since, the Tasks stack keeps this run's task definitions until the fix deploys, so the fix's *What prod's automatic rollback changes* shows them going back to the previous release, as step 4 expects. Only if the release that runs now is itself failing, read it (`Release`, as *A deploy job that was cancelled or timed out* reads it), judge it as a failed smoke, and choose with `--current` set to it (*A manual rollback*).
- When no rollback ran because the previous release is below a floor (*The plan*'s `rollback_<env>` reads `false`), a rollback across the floor is refused (`floor-crossed`), and no recorded release lies between the previous one and this run's: answer with a forward fix by PR.
- When the deploy job failed at or after its step *Services are about to change* (that step ran) and *The plan*'s `rollback_<env>` reads `true`, yet `rollback-<env>` shows as skipped, no automatic rollback ran: the rollback job reads the deploy job's `services_started` output, and that a failed job's outputs reach the jobs after it is proved only by the first such failure (TECH-SPEC T24 item 20). The failed release may be live with no record. Read what runs, as the next bullet says, and handle it as a rejected rollback: dispatch `mode=rollback` to the release `history.ts choose` gives with `--current` set to what runs (*A manual rollback*), or fix forward by PR. Report it, so the workflow is corrected by PR.
- When the rollback job was rejected, cancelled or failed, or rolled nothing back for either reason below, the failed release may be live with no record. A rollback job that rolled nothing back for one of these names it in its summary:
  - `aws-check: auto: this run's deploy replaced <release>, not the previous release (<release>) or a later one …`: a rollback landed after the gate read the records, or one whose smoke failed left an older release live with no record, so going back to the previous release would move forward past it. Choose the release afresh (*A manual rollback*, step 1, which goes by the records).
  - `aws-check: auto: a later commit (<commit>) pushed an image, so it may have migrated the database, and nothing is rolled back: check the floors at it (deploy-and-rollback.md)`: a later run pushed its image, and a deploy pushes before it migrates, so the database may have moved past a floor the gate read at this run's commit (*Floors*).

  Then read what runs. After either of those two lines it was this run's release (*Before you start*) when the check ran. Otherwise it was the deploy job's `read-back: Hearth-<env>-Services runs <release>` line when that job got so far and the rollback job deployed nothing, or else `Release`, read as *A deploy job that was cancelled or timed out* reads it, since CloudFormation may have put the run's own release back. A line of this run's holds only while no other run's deploy or rollback job has used the group (`deploy-<env>`) since: once one has (the workflow's later runs show it), read `Release` now, or take the newest `read-back: Hearth-<env>-Services` line among those runs (never a restore run's `read-back: Hearth-restore-Services` line: a restore's `prod` job uses `deploy-prod` too, but changes only the restore stage, so its line says nothing of what prod runs), and if what runs is a later run's release, that run's own smoke and rollback judge it, so roll nothing back for this run unless that release is itself failing. Dispatch `mode=rollback` to the release chosen with `--current` set to what runs (*A manual rollback*), or fix forward by PR. The gate checks what the records show, and the deploy job that the target is strictly older than what runs and that no later commit than the dispatch's has pushed an image.
- A rollback job that failed on `aws-check: the Services stack is UPDATE_ROLLBACK_FAILED …` moved nothing: the deploy's Services update failed and so did CloudFormation's rollback of it. The stack waits for tier 2 (*A stack that is stuck*); once tier 2 has continued its rollback, read what runs and judge it as above.
- When the smoke passed but the record job failed (a GitHub error), re-run the record job (*Re-running a failed job*). Until then the release is live with no record, which the pipeline allows for.

### A manual rollback

1. Choose the release. By default it is the one that ran before the current release's commit first did, never simply the record before the newest (a rollback writes a record too), and never an earlier build of the current commit, which holds the same code. In your checkout of `main`, pulled first (*Before you start*), save the environment's release records, `gh api 'repos/{owner}/{repo}/deployments?environment=<env>&task=hearth-release&per_page=100' > <folder>/records.json`, and let the release history choose: `node infra/scripts/deploy/history.ts choose --env <env> --records <folder>/records.json --current <commit>:<digest>`, the current release being what runs now: the Services stack's `Release`, which the last run that read it back names (`read-back: Hearth-<env>-Services runs <release>`), or as *When the pipeline rolled back* says after a failure. It prints `commit <commit>`, `digest <digest>` and each service's task definition, or one line, `history: refused <code>: <why>`, or, for a commit your checkout lacks, `history: <commit> is not in this clone` (pull `main` and run it again).
2. To go back to another release from the list, or when `choose` refuses, check one the same way: `node infra/scripts/deploy/history.ts validate --env <env> --records <folder>/records.json --current <commit>:<digest> --target <commit>`.
3. Check the floors: `node infra/scripts/deploy/floors-check.ts --target <commit>` prints `floors-check: allowed`, or a `floors-check: refused <migration> (<why>)` line for each floor in the way (*Floors*). `floors-check.ts` itself refuses, before it reads anything, a `--target`, a `--floors-at` or a checkout (HEAD) that isn't on the clone's `refs/remotes/origin/main`: `floors-check: <commit or HEAD> is not on origin/main`, or `floors-check: origin/main is not in this clone`, exit 2. Pull `main` and run it again; if it still refuses, stop: the commit is off `main`. The gate runs the same check; running it first saves a refused run.
4. Dispatch it in the web UI: Actions, then the deploy workflow, then Run workflow on `main`, with mode `rollback`, target `nonprod` or `prod`, release the chosen commit, and restore `none`.
5. The gate (and, for prod, `prod-gate`, which doesn't wait for CI) checks what the records show: the release is recorded in that environment with its digest, it is on `main`, and it is above every floor. The deploy job checks what runs: the release's digest isn't the one running, its commit is strictly older than what runs, and ECR still holds its image under its commit's tag. ECR keeps the newest 50 images, and past them the release can't start (`aws-check: ECR holds no image of the release under its commit's tag`).
6. It deploys the Tasks and Services stacks alone, from the release's own assembly: it never migrates and never pushes an image. Then the probe and the smoke. Prod's waits for the reviewer, after the `prod-plan` diff (*What prod's rollback changes*).
7. `record-<env>` writes a `rollback` record, its `migratedCommit` the newest migration record's commit when the record is written (a rollback migrates nothing, so it never moves back).

While a dispatched rollback waits, hold merges to `main`: a push's run can replace a pending one.

A dispatched rollback has no automatic rollback of its own. If its smoke fails, its target stays live with no record, and the newest record still names the release rolled back from, so the next forward deploy's automatic rollback rolls nothing back (`aws-check: auto: this run's deploy replaced …`, *When the pipeline rolled back*). Dispatch another rollback, chosen afresh, or fix forward.

The deploy job also refuses `aws-check: a later commit (<commit>) pushed an image, so it may have migrated the database: check the floors at it (deploy-and-rollback.md)` when an image in ECR is of a later commit than the dispatch's (a push's run since): check the floors at it (*Floors*), then dispatch the rollback again from `main`'s head.

### After a rollback outside the pipeline

After break-glass's incident rollback ([Reaching production: the break-glass role](break-glass.md#an-incident-rollback-to-an-earlier-revision)), or `HearthNonprodOperator`'s in non-prod, the services run the release gone back to while the Services stack's `Release` and the release record still name the release rolled back from.

- The first run in that environment is a manual rollback to the release the services now run (*A manual rollback*). It registers that release's revisions afresh, records it, and brings the stack into line.
- Until it has run, hold merges to `main` (a push deploys non-prod) and approve no forward prod deploy.
- A forward deploy or a drill refuses by itself meanwhile: `aws-check: the services don't run Release's image (an incident rollback outside the pipeline): dispatch mode=rollback with release <commit> first (deploy-and-rollback.md)`, naming the commit whose image the services run. A rollback may then go only to that release.
- If break-glass's step 3 found a floor at `main`'s head that this environment hasn't applied, even that rollback is refused (`history: refused floor-crossed: …`), as is any other, and the way back is a forward fix. Just before it deploys, the services go back to the task definitions they ran before, which break-glass's step 4 noted, under break-glass (its step 5's last bullet): for prod, once the fix's run waits for its approval, then approve it; for non-prod, just before the fix merges.
- A dispatched rollback still waiting when a push arrives can be replaced by the push's run, which then refuses: dispatch the rollback again.

### A deploy job that was cancelled or timed out

GitHub stops the job, not CloudFormation or a one-off task it started, and no rollback job runs after a cancelled job. Read the run's last summary line, then the Services stack's status and `Release`: from the next run's refusal, or with `aws cloudformation describe-stacks --stack-name Hearth-<env>-Services --query "Stacks[0].[StackStatus, Outputs[?OutputKey=='Release'].OutputValue | [0]]" --output text` in a break-glass session under a `drill:` reason ([Reaching production: the break-glass role](break-glass.md)), or in non-prod, while it holds synthetic data, as `HearthNonprodOperator` in your own shell.

- Still `_IN_PROGRESS`, but for `REVIEW_IN_PROGRESS`: wait. The next run refuses until it settles (`aws-check: a deployment is in progress: wait for it to settle, then dispatch again`).
- `REVIEW_IN_PROGRESS` with no `Release`: a first create whose change set never ran, as when the job was cancelled between the two. It holds no resource and never settles, so don't wait: dispatch `deploy` again, which creates the stack afresh (in prod, *A stack that is stuck* says what to do if `prod-plan`'s diff then fails).
- `UPDATE_ROLLBACK_FAILED`: the pipeline can't repair it (*A stack that is stuck*).
- Settled on the new release: judge it as a failed smoke (*When the pipeline rolled back*), and roll back or fix forward.
- Settled back on the old one: the services run what they ran. If the job got past *Deploy Platform, Data and Tasks*, those stacks hold this run's templates; in prod the next run's *What prod's automatic rollback changes* shows the Tasks stack going back, as step 4 expects.

A job cancelled or timed out in its migrate step may leave the migrate task running: see *The commit the database was migrated by*.

The pipeline also cancels its own pending jobs. Its deploy and rollback jobs share each concurrency group (`deploy-nonprod` or `deploy-prod`), which holds one running job and one pending, so a job that starts waiting cancels the one already pending, which then ends cancelled without having started: a later push's deploy job replaces an earlier one's, a rollback job replaces a later run's pending deploy job, and a deploy job a pending rollback job. A restore run's `prod` job waits in `deploy-prod` too, so it replaces a pending prod deploy or rollback job and is replaced by one, but it deploys only the restore stage: its `read-back: Hearth-restore-Services …` line is that stage's, never prod's. A cancellation that came as another of this workflow's jobs started waiting for the same group is that, never a finding. Then:

- A forward deploy replaced by a later run's deploy job needs nothing: that run deploys the newer commit. Otherwise, once the group is free, dispatch `deploy` to `prod` if no run of `main`'s head (`git fetch origin +refs/heads/main:refs/remotes/origin/main && git show-ref --verify --hash refs/remotes/origin/main`) has deployed it or is still to come.
- A rollback job replaced so was replaced by another run's deploy job, which runs next in the group. Once that job has finished, read what runs: its `read-back: Hearth-<env>-Services` line, or `Release`, read as above, if it refused or never got so far, or if it was a restore run's `prod` job, whose `read-back: Hearth-restore-Services` line is the restore stage's. If that is still this run's release, the replacing job moved nothing of this environment's, and this is handled as a rejected rollback, with `--current` set to it (*When the pipeline rolled back*). Otherwise that run moved what runs, and its own smoke and rollback judge it: roll nothing back for this run, as when another run has deployed since; only if the release that runs now is itself failing, judge it as a failed smoke and choose with `--current` set to it (*A manual rollback*).
- A restore run's `prod` job replaced so started nothing, so the restore stage is as it was: once the group is free, whoever dispatched the restore dispatches it again, a `down` the same day (*Restore up and down*, step 4).

Another workflow, a branch's included, can cancel a deploy or rollback job through the same groups, which are the repository's: a cancellation with no job of this workflow starting to wait for that group at that moment, and that nobody here made, is a finding for the quarterly review.

### A stack that is stuck

Only hearthapp's deploy role may continue, roll back or delete a stage's stack, so short of tier 2 the pipeline's next deploy of that stack is the only repair, and it repairs only some states. The deploy job's log names the stack and its status.

- `_IN_PROGRESS` but for `REVIEW_IN_PROGRESS` (a job that timed out or was cancelled while CloudFormation worked): wait for it to settle, then dispatch the same mode again. The deploy job doesn't wait for it: before then the check refuses a Services stack still moving (`aws-check: a deployment is in progress: …`), and any other stack fails the job at its change set.
- `REVIEW_IN_PROGRESS` (a create whose change set was never run, as when a first deploy's job was cancelled between the two; it holds no resource and never settles): dispatch the same mode again, which creates the stack afresh. In prod, the dispatch's `prod-plan` diffs that stack first: if the diff fails on it (how the CLI reads a stack waiting for review is one of the first runs' proofs), tier 2 deletes the stack, which holds nothing, then dispatch again.
- `UPDATE_ROLLBACK_FAILED` (a rollback that failed, as when a containment cut the execution role off mid-update): the pipeline can't continue it. The CLI's deploy first asks to roll the stack back, a prompt that a job with no terminal can't answer (`TtyNotAttached` in the log), unless CloudFormation has already refused the change set. So don't dispatch until tier 2 ([Reaching production: the break-glass role](break-glass.md#tier-2)) has continued the rollback, skipping nothing; only if that fails does it continue with the failing resources skipped. CloudFormation then marks a skipped resource `UPDATE_COMPLETE` though it no longer matches the template, so tier 2 records each in the on-call notes and makes it match again before the next deploy, as CloudFormation asks. Then dispatch the same mode again. A dispatch before then moves nothing when the stack is Services: the check refuses it before anything moves (`aws-check: the Services stack is UPDATE_ROLLBACK_FAILED (an update whose rollback failed), which waits for tier 2 (deploy-and-rollback.md)`), in every mode, a restore's (which reads prod's) and the automatic rollback's included. Any other stack so left fails the job at its change set, after the push, and still waits for tier 2.
- `ROLLBACK_COMPLETE` after a failed create: a fresh push or a dispatch of `deploy` deletes and creates a Tasks or Services stack again. A Platform or Data stack keeps its termination protection, which the CLI never turns off, so it waits for tier 2.
- `ROLLBACK_FAILED` (a failed create whose rollback failed too, so some of its resources may remain): the deploy job's check refuses a Services stack so left (`aws-check: the Services stack is ROLLBACK_FAILED (a failed create whose rollback failed), which waits for tier 2 (deploy-and-rollback.md)`). For any other stack so left, the CLI tries to delete it and create it again, which Platform's and Data's termination protection refuses. Each that remains waits for tier 2, which deletes it ([Reaching production: the break-glass role](break-glass.md#tier-2): the account moved into `Recovery`), turning its termination protection off first for Platform or Data; then dispatch the same mode again.

What the CLI does with each is read from its own code (TECH-SPEC T24 item 20), and is unproved until the first stack left so. If a run fails where this says it repairs, it fails closed: tier 2, and this section corrected by PR.

### A failed migration

From C0.12, once the Tasks stack's `HasDatabase` is on. The migrate step prints only its status lines (`migrate: applied <migration>`, `migrate: nothing to apply` and the like) and a count of the lines it withheld, then `migrate: the log may hold lines the job didn't read` when its read of the task's log stopped short of the end (it reads five pages at most, and stops at an answer it can't read). On a non-zero exit the job stops before the Services deploy, so the services still run the previous release, on the new Tasks stack's definitions, which nothing else runs. In prod, the next run's *What prod's automatic rollback changes* shows the Tasks stack going back, as step 4 expects.

- `migrate: nothing was applied; the batch rolled back`, with no `migrate: the log may hold lines the job didn't read` line: the database is as it was. Fix forward by PR.
- `migrate: the log may hold lines the job didn't read`: the status lines shown may be incomplete, so read the outcome as unknown, even beside `nothing was applied`, and take the next bullet.
- Any other line after a failure, or a task that never stopped (`migrate: the task didn't stop in time, so it is …`): the database may have moved. Read the migration record and every image's tag (*The commit the database was migrated by*), and pause deploys (*Pausing and resuming*) until the person on call has looked.
- Never roll back across it (*Floors*).

### Floors

A floor marks a contracting migration: one that removes or renames what an older release still reads. The PR that adds such a migration adds its floor to `infra/src/release/floors.ts` (an owner's read), with why and with `expansion`, the commit on `main` (the one its pull request landed as) of the expansion it follows. A rollback to a release whose migrations lack a floor's migration is refused once the floors' commit has it.

- A forward deploy migrates before it deploys Services, so the contraction would run under the release the environment runs while it still serves, and a failed Services deploy's own rollback would put that release back on the contracted database. So the gate, and `prod-gate` again for prod, refuse a forward deploy to an environment whose newest release record lacks a floor's migration and predates its expansion (`history: refused expansion-not-deployed: an environment runs a release older than a floor's expansion, so the migrate step would contract the database under it: that environment must run the expansion first`). Merge the contraction only once the expansion's own merge started its deploy run (a skip instruction in its message starts none, *Who does what*) and both environments' newest release records descend from the expansion (read each environment's records with *Before you start*'s line once the expansion's run has ended, adding `.payload.services.api` to its `--jq` list: the newest is the one whose api task definition has the highest revision, the highest id breaking a tie, as the pipeline orders them, and `git merge-base --is-ancestor <expansion> <its commit>` exits 0 for it; *The plan* shows the records as its gate read them, before its own run's record, and leaves blank an environment the run doesn't deploy), and once the newest `read-back:` line among the deploy workflow's runs for each environment does too: a manual rollback whose smoke failed writes no record but leaves its release running, and the gate reads only the records. Merge it, too, only while no run of the deploy workflow is in any of the six statuses *Pausing and resuming*'s step 4 checks (`in_progress`, `queued`, `waiting`, `pending`, `requested` and `action_required`, each printing `0`): a rollback or `drill-smoke` already under way writes its record only at its end, so the contraction's gate would pass on records that still show the expansion, and its migrate would then contract under the release the rollback puts back. A dispatch deploys `main`'s head alone, so once the contraction is on `main` no dispatch takes an environment to the expansion by itself.
- If the gate refuses `expansion-not-deployed` all the same, because no run from the expansion on has reached that environment (prod's approval rejected, or a deploy job that failed), one run may still take it there, whatever `main`'s head is now: the one exception to *Re-running a failed job*'s rule for a forward deploy. It is a run of a commit from the expansion up to, not including, the contraction (on `main`, whose history is a line, each descends from the expansion): the newest whose artifacts are under 14 days old, whose approval, if rejected, was rejected only as stale, whose failure, if its deploy job failed, is judged transient, and, in prod, since whose gate no prod release record has been written (its *The plan*'s `current_prod` is still prod's newest record: a record written since, its own pipeline rollback's among them, makes its `prod-gate` refuse `record-changed`, so it doesn't qualify). Re-run its deploy job (`nonprod`) or its `prod-plan` (prod). Its gate read the floors at a commit that lacks the contraction, so its migrate contracts nothing, and its check of what runs refuses if a later commit than its own has pushed an image to that environment (`aws-check: a later commit (<commit>) pushed an image, …`), as a run that pushed and then failed, on a throttle say, leaves behind: that commit's run is then the one to re-run, under the same conditions, and no older one. Then dispatch `deploy` again. When no such run qualifies, no pipeline path takes the environment past the expansion without contracting under the release it runs: stop, and the owner decides, by a PR that is an owner's read, whether to accept that window by naming as the floor's `expansion` the commit the environment runs.
- `floors-check.ts` refuses floors that name a file their commit lacks (`floors-check: FLOORS names <migration>, which <commit> lacks`, exit 2) and, in the gate, an expansion the clone lacks, one off `main`, or one that already holds its floor's file: correct `floors.ts` by PR.

- The pipeline reads the floors at the run's own commit (`main`'s head for a dispatch), so it may refuse a rollback for a floor whose migration the environment hasn't applied yet: fix forward. Break-glass's incident rollback can still go back there, since its floors check reads them at the newest commit that may have migrated the database, but it then says so first: until the services run what the Services stack's `Release` names again, every pipeline rollback there is refused the same way and every forward deploy for drift (*After a rollback outside the pipeline*).
- A later commit than the run's can have migrated the database since the gate read the floors: a later run pushes its image, then migrates, and may fail before its record. So every deploy job but a restore's reads every image's tag in ECR before anything moves: when one is of a commit that isn't the run's or an ancestor of it, a forward deploy or a drill refuses (`aws-check: a later commit (<commit>) pushed an image, so it may have moved the stacks or migrated the database: dispatch again from main's head (deploy-and-rollback.md)`), a dispatched rollback refuses (`aws-check: a later commit (<commit>) pushed an image, so it may have migrated the database: check the floors at it (deploy-and-rollback.md)`) and the pipeline's own rolls nothing back (`aws-check: auto: a later commit (<commit>) pushed an image, …`). The forward deploy or drill is an older run that GitHub's queue started after a later one, which may have moved Platform, Data and Tasks forward: dispatch again from `main`'s head. For a rollback, in your checkout of `main`, pulled, run `node infra/scripts/deploy/floors-check.ts --target <the chosen release's commit> --floors-at <that commit>`, which refuses either commit when it isn't on the checkout's `refs/remotes/origin/main` (`floors-check: <commit> is not on origin/main`: pull `main` and run it again, and stop if it still refuses): on `floors-check: allowed`, dispatch the rollback again from `main`'s head (*A manual rollback*), whose gate reads the floors there; on a refusal, fix forward. Only a first deploy, whose Services stack holds no release, may find no image in ECR at all; anywhere else that is refused (`aws-check: ECR holds no image, which only a first deploy may find`), and is a finding for the person on call, since ECR keeps the newest 50 images.
- The infra seams follow the same rule (TECH-SPEC T24 item 22): a PR that removes or renames an SSM parameter, a security group, a role, a log group or the cluster the Tasks and Services stacks read keeps the old one while any release among ECR's newest 50 images reads it, or says in its description that rollbacks before it are impossible. A rollback that meets a removed seam fails at its change set and leaves the current release running.
- So do the shapes an older release's assembly and profile take (TECH-SPEC T24 item 22): each run judges its environments' previous releases with its own `ASSET_CHECK` and `smoke.ts`. When `synth-previous-nonprod` fails at *Check nonprod's previous assembly*, or `synth-previous-prod` at *Check prod's previous assembly*, with an `asset-check:` line, the merged PR changed what `ASSET_CHECK` pins (a stack's properties, roles, bootstrap version or termination protection, the asset manifests' shape, the outputs and their keys, a template's sections, the resource types it may hold, its parameters and the SSM entries they name, the braces in its strings, the intrinsic functions it calls, an IAM role's keys and boundary, or CDK's custom resource and its handler's function) so that it refuses what the release before it wrote: renaming a parameter's SSM entry, taking a resource type off the list once the synth stops writing it, or, in the PR that bumps aws-cdk-lib, accepting only the new release's shape of the handler's function or a role, does that. When `synth-previous-nonprod` fails, nothing deploys, since `prod-plan` waits on non-prod's smoke. When `synth-previous-prod` fails, prod alone stops: non-prod deploys, smokes and records the release as usual (its jobs show green in the red run), so check non-prod's deploy as for any run. Either way every pipeline rollback or restore to an earlier release is refused until a further PR accepts both shapes. Don't re-run it; tell the person on call, whose PR (an owner's read) accepts the older shape beside the new one.

### Re-running a failed job

On the run's page, Re-run jobs, then the failed jobs or one job. A re-run runs only those jobs and the ones after them, with the gate's answers from the latest attempt that ran it (the first, unless the whole run or the gate itself was re-run), whose *The plan* is the one to read; each job after the gate runs its own bot test again, and a re-run gate refuses the bot (`bot-actor`), so on a bot's re-run nothing deploys. It gets a new attempt number, so a new image tag and new client tokens. A person, never Claude, may re-run:

- `record-<env>` after a failed write: it writes the record from the results of the jobs it needs, as the latest attempt each of them ran in left them (after a re-run of `prod-plan` or the deploy job, that later attempt's);
- `prod-plan`, after `prod-gate` failed and `main`'s CI, re-run, has passed: it re-runs `prod-gate` and `prod` after it;
- `nonprod` in a forward deploy (a push's run, or mode `deploy`) after a transient error, while its run's commit is still `main`'s head (`git fetch origin +refs/heads/main:refs/remotes/origin/main && git show-ref --verify --hash refs/remotes/origin/main`); once `main` has moved on, dispatch `deploy` to `prod` instead, which deploys `main`'s head (the one exception: a run that takes an environment to a floor's expansion it never reached, *Floors*). Its fast re-check and its check of what runs run again, and refuse if a later commit's release has been recorded or runs since, or a later commit has pushed an image (`aws-check: a later commit (<commit>) pushed an image, so it may have moved the stacks or migrated the database: dispatch again from main's head (deploy-and-rollback.md)`);
- `nonprod` in a dispatched rollback or drill after a transient error, whether or not `main` has moved, since the re-run checks everything again: it refuses if non-prod's release records changed since the gate read them (`fast re-check: nonprod's release records changed since the gate read them`), if a rollback's target is now the release running or not strictly older than it, or a drill's release isn't what runs, or if a later commit has pushed an image (a rollback's line ends `check the floors at it`: *Floors*). A `drill-break` also refuses, before it calls the CLI, once its broken deploy has reached CloudFormation, since the Services stack's last operation then didn't succeed (`drill-break: the Services stack is <status> before the drill, …`), so re-running one helps only after a failure before its deploy changed the stack. After a refusal, dispatch the same mode again from `main`'s head: a rollback with its release chosen afresh (*A manual rollback*), never a forward deploy in its place, which would deploy `main`'s head rather than the release the rollback was for; a drill as it is, but for two refusals that a dispatch as it is meets again, each answered first by a forward deploy, `deploy` to `nonprod`, as *The rehearsal* says: a `drill-smoke` whose gate refuses `drill-not-forward` (a rollback was recorded meanwhile), and a `drill-break` refused on its Services stack's status, which needs that deploy and then a fresh `drill-break`; where a fresh drill refuses `aws-check: what runs is not the release the gate read` again, non-prod runs a release its records don't name, so settle that first, as for a restore (below). Hold merges meanwhile, as for any dispatched rollback;
- for a prod deploy or a prod rollback, `prod-plan` in place of `prod`, a deploy's only while its commit is still `main`'s head (but for a floor's expansion: *Floors*) and a rollback's whether or not `main` has moved: it re-runs `prod-gate`, `prod` and the jobs after them, and the reviewer reads its fresh diff before approving again. `prod-gate` re-validates a rollback's target against prod's records read afresh (`history: refused record-changed` when its recorded digest has changed, or `floor-crossed`: choose the release afresh and dispatch it). `prod` re-run on its own, by "Re-run failed jobs", or after `prod-gate` re-run on its own, keeps `prod-plan`'s diff from the earlier attempt (and `prod-gate`'s read too, unless `prod-gate` was re-run), so its fast re-check refuses before any credential (`fast re-check: prod-plan's diff is from another attempt of this run: re-run prod-plan, which re-runs prod-gate and this job after it, or, once a prod release has been recorded since this run's gate, re-run all jobs (while the commit is main's head) or dispatch afresh (deploy-and-rollback.md)`). It also refuses when prod's newest release record has changed since `prod-gate` read it (`fast re-check: prod's release records changed since prod-gate read them`), as after a rollback or another run's record, and, once it holds its credentials, when a stack of the stage has changed since `prod-plan` read it before its diff (`plan-basis: Hearth-<stage> changed since prod-plan diffed it`), recorded or not: re-run `prod-plan` again, or dispatch afresh. When another run's `prod`, a rollback or a record changed prod meanwhile, re-run all of the run's jobs instead (a deploy's while its commit is `main`'s head), or dispatch afresh: `prod-plan` re-run alone keeps the gate's read of prod's records, so its `prod-gate` refuses (`history: refused record-changed`) once a release was recorded since the gate (*On approving*);
- for a restore, `prod-plan` in place of `prod`, after a transient failure alone: it re-runs `prod-gate`, `prod` and the jobs after them, and the reviewer reads its fresh diff of the restore stage before approving again. `prod` re-run on its own keeps `prod-plan`'s diff from the earlier attempt, so its fast re-check refuses, as for a prod deploy. When its fast re-check refused because prod's records changed (`fast re-check: prod's release records changed since prod-gate read them`), or an `up`'s check found prod running another release than the gate read (`aws-check: what runs is not the release the gate read`), re-running refuses again, since each compares with what the gate read: dispatch the restore afresh. A fresh dispatch's gate reads prod's newest release record again, so when an `up` refuses `what runs is not the release the gate read` again, prod runs a release its records don't name: one whose record write failed, one a rejected, cancelled or failed rollback left live, or a dispatched rollback's target whose smoke failed (*When the pipeline rolled back*, *A manual rollback*). Settle that first, so that a record names what runs: re-run `record-prod` after a failed write (above), or else take prod to a recorded release as those sections say. Then dispatch the restore.

A smoke (`smoke-<env>`) or a resmoke (`resmoke-<env>`) is never re-run on its own, whether it failed or passed. It judges only the read-back its deploy or rollback job wrote in the same attempt, and a re-run alone keeps that job's read-back from an earlier attempt, so it refuses (`smoke: the read-back is from another attempt of this run: re-run the job that wrote it, or dispatch afresh`) and fails. In a forward deploy (and a `drill-smoke`), a smoke's failure starts its rollback job, which rolls back only if this run's release still runs (and in prod waits for the reviewer). To retry a forward deploy's smoke, re-run its deploy job (in prod, `prod-plan`, as above), which deploys again (no change if nothing moved since; after the pipeline rolled back, see below), reads back afresh, and runs the smoke after it. A dispatched rollback whose smoke failed has neither: no rollback job runs, and its target stays live with no record, so re-running its deploy job (in prod, `prod-plan`, whose diff then shows no change) is refused before anything moves (`aws-check: the target is the release running now`). Don't re-run it, or approve it again: dispatch another rollback, chosen afresh, or fix forward (*A manual rollback*).

After the pipeline rolled back, what "Re-run failed jobs" does depends on what started the rollback:

- A failed smoke (the deploy job green, its smoke red): it re-runs the smoke, which refuses, and the rollback job, which finds this run's release no longer runs and rolls nothing back, so the run stays red and writes no record. Fix forward or dispatch afresh.
- The deploy job's own failure once its Services deploy began (the deploy job red, as at its probe or its read-back): in non-prod it re-runs the deploy job, which deploys again the release the pipeline just rolled back from and, if its smoke then passes, records it and goes on to stage prod, as a dispatch of `deploy` of that commit would. In prod it re-runs `prod`, whose fast re-check refuses (`prod-plan`'s diff is from another attempt), so nothing moves and the run stays red. To deploy that release again in prod: once the pipeline's rollback was recorded (`record-prod` wrote its `pipeline-rollback`, the usual end when `resmoke-prod` passed), `prod-plan` re-run alone refuses at `prod-gate` (`history: refused record-changed`), since a re-run keeps the gate's read of prod's records, so re-run all of the run's jobs, whose fresh diff shows that release, or dispatch `deploy` to `prod`; re-run `prod-plan`, whose fresh diff shows it, only when no prod release record has been written since the gate (the rollback was rejected, rolled nothing back or its resmoke failed). Then approve `prod` again. Use any of these only for a failure judged transient, and only while the run's commit is still `main`'s head; otherwise fix forward or dispatch afresh. In prod, the approval deploys the release that just failed again: never approve it as though nothing would move.

Re-run nothing older than its artifacts (14 days): dispatch afresh instead.

### Pausing and resuming

A repo admin, in the web UI (Actions, then the deploy workflow, then Disable workflow), or with `gh` as the separate operating-system user (*Before you start*):

1. Notes `main`'s head (`git fetch origin +refs/heads/main:refs/remotes/origin/main && git show-ref --verify --hash refs/remotes/origin/main`), then disables the workflow: `gh workflow disable deploy.yml`.
2. Rejects any run whose deploy job (`nonprod` or `prod`) waits for its approval (`waiting`), on its page, noting its commit: rejecting it starts no rollback job. A run whose `rollback-<env>` job waits is a failed release that is still live: the owner approves it (*When the pipeline rolled back*), and it finishes as in step 3; a rollback never migrates.
3. Lets a running one finish. It may be cancelled (Cancel workflow on its page, or `gh run cancel <run id>`) only while none of its deploy jobs has reached its migrate step or its probe: a one-off task already started runs on after its job is cancelled, and a migrate finishing then writes no migration record.
4. Then sees no run of it in any of six statuses: for each of `in_progress`, `queued`, `waiting`, `pending`, `requested` and `action_required`, `gh run list --workflow deploy.yml --status <status> --json databaseId --jq length` prints `0`.

To resume:

1. Enable the workflow: `gh workflow enable deploy.yml`.
2. If a rollback the pause met was rejected or failed, the release that failed is live: follow *When the pipeline rolled back* first.
3. Dispatch `deploy` to `prod` only if `main`'s head now (`git fetch origin +refs/heads/main:refs/remotes/origin/main && git show-ref --verify --hash refs/remotes/origin/main`) differs from the one noted when pausing, since pushes made while the workflow was disabled were never queued, or if pausing rejected or cancelled a forward deploy (a push's run, or mode `deploy` to `nonprod` or `prod`); a rejected rollback, drill or restore is dispatched again by whoever wanted it. Otherwise do nothing, however the release records read: after any rollback an environment's newest record names an older commit than `main`'s head, which is no missed push, and a dispatch would deploy the release that was rolled back. A dispatch builds and deploys both environments again under a new digest, and asks for prod's approval.

Every run of the Owner bootstrap script happens inside such a pause ([Setting up the organisation and its first Owner](first-owner-set-up.md#running-the-owner-bootstrap-script)), and so does the set-up runbook's cut-off of the GitHub roles before an owner's rename ([Setting up the AWS organisation and its accounts](aws-account-set-up.md#e-githubs-oidc-subject-and-the-rest-of-the-configuration)).

### The commit the database was migrated by

`gh api 'repos/{owner}/{repo}/deployments?environment=<env>&task=hearth-migrated&per_page=1' --jq '.[0].payload.commit // "none"'` prints the newest migration record's commit, or `none` when no migration has run there (no database yet: C0.11). It is the newest release record's `migratedCommit`, or newer after a run that failed once it had migrated, unless a pipeline rollback has recorded since.

The record can lag the database: a migrate task that finished after its job was cancelled or timed out writes none. A deploy pushes its image before it migrates, so every commit that has migrated the database pushed an image first. Go by every image's commit, never the newest image by `imagePushedAt`: push order is commit order only while every deploy job refused to push behind a later commit's image, and ECR doesn't document whether a re-tag moves an image's push time. So, in the break-glass session the Owner bootstrap script's run opens anyway, list every image's commit, from its tag (`sha-<commit>-<run id>-<attempt>`), in that account's ECR: `aws ecr describe-images --repository-name hearth-server --query 'imageDetails[].imageTags[]' --output json | jq -r '[.[] | strings | capture("^sha-(?<c>[0-9a-f]{40})-[0-9]+-[0-9]+$").c] | unique[]'`. With the record's commit (unless it printed `none`), each checked to be 40 lowercase hex digits before you paste it and pasted quoted, take, in your checkout of `main`, fetched first by `main`'s full name (`git fetch origin +refs/heads/main:refs/remotes/origin/main`), the one every other is an ancestor of: `if m=$(git show-ref --verify --hash refs/remotes/origin/main); then n=; bad=; for c in "<commit>" "<commit>" …; do if ! printf '%s\n' "$c" | grep -qxE '[0-9a-f]{40}' || ! git cat-file -e "$c^{commit}"; then bad=1; elif ! git merge-base --is-ancestor "$c" "$m"; then echo "off main: $c"; elif [ -z "$n" ] || git merge-base --is-ancestor "$n" "$c"; then n=$c; elif ! git merge-base --is-ancestor "$c" "$n"; then bad=1; fi; done; [ -z "$bad" ] && [ -n "$n" ] && echo "$n" || echo stop; else echo stop; fi` prints it. A line `off main: <commit>` names a commit that isn't on `main`, which only a forged record names: a migration record is data that anything with Deployments write can add, a branch's workflow included, while the pipeline pushes and deploys only `main`'s commits. The loop leaves it out; never paste it onward, and note it for the quarterly review. If it is the current release's commit or an image's, stop. If it prints `stop`, one of them isn't a commit's 40 hex digits, the checkout lacks one of them or has no `refs/remotes/origin/main` (fetch `main` as above and run it again), or two aren't on one line, which on `main` never happens: stop and tell the person on call. The loop names `main` by its full ref, never `origin/main`, and the fetch names it by its full refspec, never `main`: a tag of either name, which anyone who can push a branch can push, would stand in for `main` in a short name's lookup (git only warns that the name is ambiguous), and a forged record's commit would then read as on `main`. No later commit has migrated the database, but this one may not have either (a run that pushed and then failed before its migrate applied anything). The Owner bootstrap script refuses any other checkout than the one the database was migrated by, by comparing its migrations with the database's both ways and naming the difference: a checkout taken before the session that turns out older is taken again at the newer commit, and one that holds a migration the database hasn't applied is taken again at the next older commit among those listed, until the script accepts it, the run starting again each time.

### The rehearsal

The rollback rehearsal (C11-D59), dispatched in the web UI: on non-prod before prod's first workload deploy (TECH-SPEC T24 item 5), on prod the same week, then quarterly. Each rollback in it goes back to a recorded release of an older commit, so before step 2 non-prod's release records name at least two different commits. The pipeline's first run records one, so merge at least one more PR first (its run's prod approval left waiting or rejected, as for the first run's); a dispatch of `deploy` rebuilds the same commit and doesn't count. `drill-smoke` also runs only straight after a passed forward deploy of `main`'s head to non-prod: non-prod's newest release record must be a `deploy` of the run's commit, since the drill deploys Platform, Data and Tasks from that release's assembly, and after a rollback those would be older than the ones that run. A `drill-smoke` refused `no-earlier-release` (non-prod's records name one commit only, however many builds of it) or `drill-not-forward` (the newest record is a rollback, or a forward deploy of an older commit) means this isn't met yet: merge, or dispatch `deploy` to `nonprod`, first. On non-prod:

1. `drill-break`: it deploys non-prod's Services with realtime unable to start, and passes when that deploy fails and CloudFormation and the circuit breaker put realtime back on the revision it ran (`drill-break: the broken deploy failed and realtime runs <family:revision> again`); then the smoke passes. Expect an A14 email. The run is green when the drill passed. Afterwards the person on call, in a break-glass session under a `drill:` reason, lists realtime's family's `ACTIVE` revisions, `aws ecs list-task-definitions --family-prefix hearth-nonprod-realtime --status ACTIVE`, and notes for C0.11 PR 5's record, by revision number alone and never an ARN, whether the drill's own revision (the one whose `LOG_LEVEL` is `drill`, read as the incident rollback's step 2 reads a revision) stays among them. If it does, the incident rollback names it to `history.ts choose-ecs` with `--drill`, so it is never chosen. `drill-break` starts only on a Services stack whose last operation succeeded (`UPDATE_COMPLETE` or `CREATE_COMPLETE`), since only then does the stack's status afterwards show that this deploy reached CloudFormation. On any other it refuses (`drill-break: the Services stack is <status> before the drill, so its status after couldn't show this deploy reached CloudFormation: dispatch deploy to nonprod first (deploy-and-rollback.md)`) before it calls the CLI, so nothing changes and no A14 email comes. So a second `drill-break` straight after a passed one, or one after a forward deploy that CloudFormation rolled back and nothing has deployed Services since, needs a forward deploy first: dispatch `deploy` to `nonprod`, whose new image changes the Services template, then `drill-break` again. A `drill-break` that fails (that refusal, `drill-break: the broken Services deploy succeeded, so the drill proved nothing`, `drill-break: realtime isn't back on the revision it ran`, or `drill-break: the Services stack is <status>, not UPDATE_ROLLBACK_COMPLETE`) has no rollback job. After a broken deploy that succeeded, dispatching it again changes nothing: the same drill template is synthesised, the CLI finds no change, and the step fails the same way. Answer it with a forward deploy: dispatch `deploy` to `nonprod`, which deploys `main`'s head and replaces the drill's Services template and realtime's revision (a stack left `_FAILED` goes as *A stack that is stuck* says first). Note the drill's revision as above, for C0.11 PR 5 and the incident rollback's `--drill`, and correct the drill by PR (TECH-SPEC T24 item 22).
2. `drill-smoke`, straight after a passed forward deploy of `main`'s head to non-prod: the normal deploy path with non-prod's current release (no change and no migrate), the probe, then the smoke, inverted on SMK-05, fails on purpose; `rollback-nonprod` deploys the release that ran before, `resmoke-nonprod` passes and `record-nonprod` writes a `pipeline-rollback` record. The run ends red by design, and non-prod is left on the earlier release. Hold merges from its dispatch until `record-nonprod` has written that record (or the run has ended): a merge's gate meanwhile reads records that still show non-prod on the forward release, so a contraction would pass it (*Floors*). A second `drill-smoke` needs a forward deploy (dispatch `deploy` to `nonprod`) first.
3. A forward deploy: dispatch `deploy` to `nonprod`.
4. A rollback outside the pipeline, by someone holding `HearthNonprodOperator`, following break-glass's incident rollback while GitHub can be read.
5. A dispatch of `deploy` to `nonprod`, which must be refused for drift (*After a rollback outside the pipeline*).
6. A dispatch of `rollback` to the release the services now run, which must pass.
7. A forward deploy (dispatch `deploy` to `nonprod`), then a manual rollback (*A manual rollback*) to the release `history.ts choose` gives, then a forward deploy again. The forward deploy comes first because steps 2 to 6 leave non-prod on the older commit, which may have no recorded release before it.

On prod, the same week, once a merge after prod's first deploy has reached prod with the approval, so that prod's release records name two different commits: one manual rollback to the release before it, with the approval, then one forward deploy (dispatch `deploy` to `prod`). C0.11 PR 5 records the dates and run numbers in TECH-SPEC T24 item 34.

### Restore up and down

The restore stage (C11-D45), in prod's account:

1. Dispatch mode `deploy`, target `restore`, restore `up`, and `down` too (step 4), only while no prod deploy or rollback job, automatic or dispatched, is waiting to run (for `deploy-prod` or for its approval): the restore's `prod` job waits in `deploy-prod` too, and can replace it (*A deploy job that was cancelled or timed out*). The gate needs a prod release record: the restore runs prod's newest release record, already in prod's ECR, and renders the restore stage's Platform and Data from that release too. So an `up` runs only while prod runs that release: while prod runs one its records don't name, it refuses (`aws-check: what runs is not the release the gate read`) until a record names what runs (*Re-running a failed job*, its restore bullet). After a prod rollback that record is older than prod's own Platform and Data, and a restore at an older release than the stage last ran can leave behind a named log group the newer one added, which then blocks the next `up` until tier 2 removes it.
2. `prod-plan` diffs the restore stage as this direction's assembly renders it against what prod's account holds, through `hearth-gh-diff`: for `up` its four stacks (`restore/*`), for `down` each stack `down` deploys, one at a time, in its order (Services, Data, Platform), decided by its status as `down` decides it. A `down` stack that doesn't exist, that a failed create left (`ROLLBACK_COMPLETE`, `REVIEW_IN_PROGRESS`) or that is `ROLLBACK_FAILED` isn't diffed, since `down` skips it: a line above the heading names it instead (`restore down: Hearth-restore-<Part> … isn't diffed`). Before any diff, `prod-plan` reads every stack of the stage, Tasks included (step 4's `plan-basis:` read), for `up` and `down` alike: one still moving fails it (`plan-basis: Hearth-restore-<Part> is <status>: wait for it to settle, then re-run prod-plan`), as does one whose status can't be read (`plan-basis: Hearth-restore-<Part> can't be read`), so `prod` never starts. Once the stack has settled, and no `up` is in flight, re-run `prod-plan` (*Re-running a failed job*, its restore bullet) or dispatch again. A `down` stack that starts moving after that read and before `down`'s diff reads it fails the diff the same way, with the diff's own line (`restore down: … is <status>, which down refuses, so the diff fails: wait for it to settle, then dispatch again`, or `… can't be read, so the diff fails`). What `prod-plan` read of each stack binds `down`: after the approval, `down` reads every stack again before it deploys anything and refuses unless it reads what `prod-plan` read (`restore down: the restore stage changed since prod-plan diffed it (prod-plan read …, down reads …), so nothing is taken down: dispatch restore=down again`), so it never deploys a stack its diff didn't show, one another restore's `up` made or made again in between; and, as for every prod approval, `prod` reads each restore stack's status and when it last changed once it holds its credentials, and refuses unless it reads what `prod-plan` read before its diff (`plan-basis: Hearth-restore changed since prod-plan diffed it`), so an `up` that updated the stage in between, which leaves every status `UPDATE_COMPLETE` as before, stops it too: dispatch `down` again then. So approve a restore only while no other restore run is in flight, dispatch `down` only once the `up` run has ended, and when `down` refuses so, dispatch it again and read the fresh diff. The diff goes into its summary, *What the restore changes*, as one code block as a deploy's is (step 4 of *A release, from merge to prod*). Read *The plan* first, in the gate's own summary (the box headed `gate`, never one a `build` or synth job wrote): the direction, the commit and the digest. Then read the diff, in `prod-plan`'s own summary or its *Diff* step's log, and approve the run's `prod` job as for a prod deploy only if every change is the restore stage's own: its stacks created or updated for `up`, their running parts removed for `down`. An `up` or a `down` renders prod's newest release record when it is dispatched, so when that record has moved since the stage last ran (a prod deploy or rollback in between), the diff also carries the restore stage's own templates to that release: its task definitions' image and its `Services` stack's `Release` output among them, as the run that took prod to that release changed prod's (its diff, in its own `prod-plan` summary). That is expected, and still the restore stage's own. Reject a change that names anything of prod's own (a role, a security group, a policy or a stack whose name holds `-prod-`), however it is labelled; a restore's templates are a release's own code, which no forward diff showed. An added resource shows only its type, path and name, never what it names, so reject one that no PR adds to the restore stage. Step 4's rule for a custom resource and a function holds here too, with its exception: the `up` that creates `Hearth-restore-Platform` adds its custom resource, handler function and role. Before the first restore, prod's Baseline must hold `hearth-gh-diff`'s read of the restore stage's stacks, which the person on call deploys once C0.11 PR 4 has merged, under break-glass with `lz:pr-<that PR's number>` ([Setting up the AWS organisation and its accounts](aws-account-set-up.md#r-before-the-first-workload-deploy), step R.8, and [Reaching production: the break-glass role](break-glass.md)'s *A Baseline deploy under `lz:pr-N`*); until it does, `prod-plan`'s diff fails, so `prod` never starts and the restore waits.
3. It deploys the restore stage's Platform, Data, Tasks and Services, Valkey and five endpoints among them (about 20 minutes), then the probe, which raises A7 in prod (expected), and the read-back. `smoke-prod` checks the services' half of SMK-06, and `record-prod` writes a `hearth-restore` record, `up`.
4. The same day, once the `up` run has ended, dispatch restore `down`, since an active stage costs about USD 2 a day. It deploys Services, then Data, then Platform, each only if it exists and has settled, with no probe, and `record-prod` writes a `hearth-restore` record, `down`. `down` takes only the restore stage's own stacks down, so it compares no release of prod's and works while prod runs a release with no record; it still waits while prod's Services stack is moving (`aws-check: a deployment is in progress: wait for it to settle, then dispatch again`), and while it is left `ROLLBACK_FAILED` or `UPDATE_ROLLBACK_FAILED`, until tier 2 has dealt with it (*A stack that is stuck*).

### A restore that failed

An `up` that failed or timed out leaves its stacks wherever CloudFormation took them, and costs money while Valkey and the endpoints exist. Dispatch `down` the same day, once that run has ended, and never while an `up`'s retry is in flight (`down` refuses a stage that changed since its `prod-plan` read it, step 2 of *Restore up and down*). It deploys Services, Data and Platform in that order, each only if it exists and has settled: it skips one that doesn't exist (`restore down: Hearth-restore-<Part> doesn't exist, so it is skipped`) or that a failed create left, in `ROLLBACK_COMPLETE` or `REVIEW_IN_PROGRESS` (`… is what a failed create left, so it is skipped`), which holds nothing billed, and never deploys one still moving. A stack moving when `down` is dispatched fails its `prod-plan` (`plan-basis: Hearth-restore-<Part> is <status>: wait for it to settle, then re-run prod-plan`, step 2 of *Restore up and down*), so `prod` never starts: once it has settled, re-run `prod-plan` or dispatch `down` again. One that starts moving after `prod-plan` diffed it makes `down` refuse before it deploys anything, with step 2's `restore down: the restore stage changed since prod-plan diffed it (…)` line, whose `down reads …` names that stack's `_IN_PROGRESS` status: wait for it to settle, then dispatch `down` again. Only something outside the run starts a stack moving while `down` itself runs, and then `down` stops at that stack (`… is <status>: wait for it to settle, then dispatch again`), with the stacks before it already taken down: wait, then dispatch again. Its diff in `prod-plan` shows only what it deploys, each stack it skips named above the diff instead (step 2 of *Restore up and down*), so a `down` after a failed `up` shows only the running parts of the stacks the `up` left removed, which step 2's rule approves. Its read-back reads a restore Services stack so left, or one that doesn't exist, as the release `down` was given, so the run ends green. One whose failed create couldn't roll back either, `ROLLBACK_FAILED`, may still hold billed resources: `down` skips it too (`restore down: Hearth-restore-<Part> is ROLLBACK_FAILED (a failed create whose rollback failed), so it is skipped: it may hold billed resources and waits for tier 2`), takes the later stacks down, then fails (`restore down: the restore stage isn't down: tier 2 deletes Hearth-restore-<Part> … (deploy-and-rollback.md)`) and writes no `down` record. Tier 2 ([Reaching production: the break-glass role](break-glass.md#tier-2)) deletes that stack the same day, turning its termination protection off first for Platform or Data; then dispatch `down` again. A restore Platform or Data stack that a failed first create left in `ROLLBACK_COMPLETE` waits for tier 2 to remove it before the next `up`, since its termination protection refuses the CLI's delete; one left in `REVIEW_IN_PROGRESS` holds no resource, and the next `up` creates it afresh. A restore stack left `UPDATE_ROLLBACK_FAILED` (an update whose rollback failed) is handed to the CLI, which can't continue it (*A stack that is stuck*), so `down` fails there, before the stacks after it, and Valkey and the endpoints may still be billed: tier 2 continues its rollback the same day, then dispatch `down` again.

## Check it worked

- The run is green, but for a `drill-smoke`, which ends red by design.
- The environment's newest `hearth-release` record names the release and its `services`.
- The Services stack's `Release` output equals it: from the run's summary (`read-back: Hearth-<env>-Services runs <release>`), or in a break-glass session under a `drill:` reason.
- After a rollback, both name the release gone back to.
- After a restore `down`, the restore stage's services show a desired count of 0 (the read-back, and `smoke-prod`'s SMK-06), or none where `down` skipped their stack.

## Afterwards

- Reject a stale waiting approval of a deploy (never a waiting `rollback-<env>`, whose failed release is live: *When the pipeline rolled back*): a run waiting for its approval may hold `deploy-prod` (the first runs show whether it does) and so block later prod deploys until it is approved or rejected.
- Note in the on-call notes a deploy or rollback job that nobody here cancelled and no job of this workflow replaced (*A deploy job that was cancelled or timed out*), one that stopped at *The artifacts' names* or its download within 14 days of its run's start (an artifact gone early, which a workflow holding Actions write, a branch's included, can delete: TECH-SPEC T24 item 21; a rollback so stopped is handled as a failed one, *When the pipeline rolled back*), one that stopped there with `artifacts: this run makes … and its id is empty` (the job that makes that artifact succeeded and named none: read that job's log, and the release whose code it ran, before any re-run), and a rollback outside the pipeline not yet reconciled.
- Each quarter, the second reviewer reconciles the deploy roles' sessions with the deployments ([The quarterly review of break-glass uses](break-glass-review.md), step 6).
- Keep to the calendar (*Upkeep*).

## Don't

- Approve from a terminal, or approve a run whose diff and plan you haven't read.
- Approve a forward deploy while a rollback outside the pipeline is unreconciled.
- Edit an environment or its reviewers in the web UI rather than by PR and `scripts/protect-environments.sh apply`. The exceptions are what `apply` can't do: setting secrets (only the web UI or `gh secret set` sets them), removing a custom protection rule that `check` names, and deleting an environment that `check` names under another case before `apply` runs again ([Setting up the AWS organisation and its accounts](aws-account-set-up.md), step E.4).
- Write or delete a deployment by hand.
- Re-run a prod deploy's, rollback's or restore's `prod` or `prod-gate` on its own: `prod`'s fast re-check refuses `prod-plan`'s diff from an earlier attempt. Re-run `prod-plan`, for a deploy only while the run's commit is still `main`'s head, for a rollback or a restore whether or not `main` has moved (*Re-running a failed job*).
- Answer a failed or refused rollback with a forward deploy: dispatch `rollback` again, its release chosen afresh. A drill is the other way round: a `drill-smoke` refused `drill-not-forward` waits for a forward deploy to non-prod, and a failed `drill-break` is answered by one (*The rehearsal*).
- Re-run a smoke or a resmoke on its own, whether it failed or passed: it refuses a read-back from an earlier attempt and fails (*Re-running a failed job*).
- Cancel a run past its migrate step or its probe.
- Roll back past a floor.
- Merge a contraction before both environments run its expansion (*Floors*).
- Leave the restore stage up.
- Give any Claude Code session a token with Deployments write, Actions write or Administration, or browser or computer control over a GitHub sign-in that can approve prod, or sign `gh` in with such a token, or leave one anywhere git finds a github.com credential (a credential helper, a URL or an `insteadOf` rewrite, an `extraHeader`, an askpass program such as an editor's terminal sets, or `~/.netrc`), as the operating-system user Claude Code runs as (*Before you start*; [Setting up the AWS organisation and its accounts](aws-account-set-up.md), step E.4, reads each back).
