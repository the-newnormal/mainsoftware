# Setting up the AWS organisation and its accounts

## Use this when

- Building the landing zone for the first time: the organisation, its four accounts (management, log-archive, non-prod and prod), Identity Center, the guardrails, the organisation trail, break-glass and the alarms (TECH-SPEC T24 items 1 to 8, 11 and 17).
- Redoing one of its manual steps, which sit outside code and can drift.
- A tier-2 change: switching the log buckets to COMPLIANCE, any change to `Hearth-LogArchive`, or upgrading any account's bootstrap (step Q).
- A later deploy of `Hearth-Foundation` after a reviewed PR (step K's deploy, under `HearthOrgAdmin`).
- The quarterly read-backs (*Check it worked*).

## Who does what

- The owner, as the organisation's administrator, runs every AWS step: steps A to D and the start of H as the management account's root user, signed in to the console with its security keys, the only identity the management account has until then, then with the temporary `HearthSetUp` permission set, then with `HearthOrgAdmin`.
- A repo admin sets GitHub's OIDC subject customisation for this repository and reads it back (step E).
- The DPO confirms that the AWS transfer entry's facts name the United States for AWS's global services (Identity Center's sign-in events and the global services' CloudTrail events are first recorded in us-east-1, and GuardDuty runs there too).
- The person on call runs the A1 drill (step P).
- The second reviewer sees every alarm the set-up raises in the first quarterly review ([The quarterly review of break-glass uses](break-glass-review.md)).
- A coding agent runs no step, and never sees an account id, a `.env.local` line or a command's output.

## Before you start

- An encrypted, up-to-date machine.
- A separate operating-system user for the landing-zone and break-glass shells, one user for all of them, or at least a dedicated home folder for each (mode 700, `mkdir -m 700`), with no Claude Code session running under it. That user owns the checkout: `cdk diff` and `cdk deploy` with `--app` naming the assembly write a read lock into it (`read.<pid>.<n>.lock` in `cdk.out`), so the shell that deploys runs as the user that synthesised, and a checkout another user owns stops them with `EACCES`. Two shells:
  - the **credential-free shell**, with no AWS credentials, profile or SSO session at all (`env | grep '^AWS_'` prints nothing, and its AWS config and credentials files are empty or point at `/dev/null`), where every synth runs. On a cloud machine with a role of its own (an EC2 instance profile, say), the instance metadata service hands that role's credentials to any process that asks, which `env` can't show, and the CDK CLI would use them: step F's synth turns that off for itself (`AWS_EC2_METADATA_DISABLED=true`, as `synth:lz` does), and such a machine is better not used;
  - the **credentialed shell**, in its own folder, whose AWS config holds this set-up's Identity Center profiles (and, from step J, a profile per member account that assumes `OrganizationAccountAccessRole` from the management session), where `cdk diff`, `cdk deploy`, `cdk bootstrap` and the `aws` commands run. Account ids live only in that config and in `infra/.env.local`.
- AWS CLI version 2, Node 24.12 or later, `jq`; two FIDO2 security keys.
- The role mailboxes (C11-Q07): one per account root, on the organisation's domain, and the ops mailbox that reaches the person on call, the second reviewer and the DPO.
- C11-Q08's two domain names committed in `DOMAINS` in `infra/src/config/profiles.ts` by a reviewed, owner's-read PR: every real target refuses the `.invalid` placeholders, so nothing here deploys before they are.
- C11-Q09's budget amounts.
- A fresh checkout of `main` at the merged PR, installed with `npm ci --ignore-scripts`.
- `infra/.env.local`, copied from `infra/.env.example` and filled in as the steps give each value, readable by that user alone (mode 600), never committed, and never pasted into a chat, an issue, a PR or a coding agent's session.
- The AWS CLI's history off in both shells: `aws configure get cli_history` prints nothing or `disabled`.

## Steps

The order matters, and each step says why it comes where it does, so a later re-run keeps it. Steps A to D, and H's first part, run as the management account's root user, signed in to the AWS console with its security keys: until `HearthSetUp` exists it is the only identity the management account has. It works only in that console session, on the console's own pages or, where a step gives commands, in AWS CloudShell opened from it: it never has an access key, and the credentialed shell holds no profile for it. Nothing after uses it.

### A. The management account

1. Secure the management account's root user: register both FIDO2 keys (one stays with the founder, the other goes to the second sealed place), and remove any access key; never create one. A2 alarms on every root action once the trail exists.
2. Create the organisation with all features.
3. Enable the policy types on the root: service control policies, resource control policies and AI services opt-out policies.
4. Enable trusted access for IAM and centralised root access, before any member account exists, so every member account is made with no root password or keys: on IAM's *Root access management* page, with both of its features on (root credentials management, and privileged root actions in member accounts), which also enables IAM's trusted access; or in CloudShell, `aws organizations enable-aws-service-access --service-principal iam.amazonaws.com`, then `aws iam enable-organizations-root-credentials-management` and `aws iam enable-organizations-root-sessions`.
5. Write the organisation's id and its root's id into `infra/.env.local` (`HEARTH_ORG_ID`, `HEARTH_ORG_ROOT_ID`).

### B. The OUs

Create three OUs under the root: `Security`, `Workloads` and `Recovery`. Write their ids into `infra/.env.local` (`HEARTH_OU_SECURITY`, `HEARTH_OU_WORKLOADS`, `HEARTH_OU_RECOVERY`). `Recovery` stays empty but while tier 2 holds an account there.

### C. The accounts

Create log-archive, non-prod and prod one at a time, each with its own role mailbox: on Organizations' *Add an AWS account* page, waiting until each shows as active, or in CloudShell, `aws organizations create-account`, then `aws organizations describe-create-account-status` until it succeeds. Write each id into `infra/.env.local` (`HEARTH_ACCOUNT_*`, management's too). Each stays in the root until its own step moves it: while it sits there, `OrganizationAccountAccessRole` (OAAR) can set it up, and once it is in its OU nobody can use OAAR there.

### D. Identity Center

1. Enable Identity Center's organisation instance in management, with ap-southeast-1 as its home Region and the built-in directory.
2. Require MFA at every sign-in, allowing only security keys and passkeys.
3. Set the access portal's session to the shortest Identity Center allows (1 hour), not the 8-hour default, and write down the shortest it offered for TECH-SPEC T24 item 3.
4. Create the five groups (the org admins, the on-call group, the non-prod operators, the reviewers and billing) and add their people by hand: names are personal data and never reach the repository. Write the instance's id, the identity store's id and each group's id into `infra/.env.local` (`HEARTH_SSO_INSTANCE_ID`, `HEARTH_IDENTITY_STORE_ID`, `HEARTH_GROUP_*`).

### E. GitHub's OIDC subject, and the rest of the configuration

Every synth reads the whole configuration, so it is complete before the first one. The Baselines' deploy roles trust one exact subject each, so the repository's subject format is fixed here.

1. A repo admin sets the repository's OIDC subject customisation to include `job_workflow_ref` (`gh api -X PUT repos/{owner}/{repo}/actions/oidc/customization/sub` with `use_default` false and the claim keys `repo`, `context` and `job_workflow_ref`), then reads it back with `gh api repos/{owner}/{repo}/actions/oidc/customization/sub`, which prints `use_default` false and those three claim keys, in that order. It prints no subject.
2. The owner writes the subject those keys make into `HEARTH_GITHUB_SUBJECT_FORMAT`, with the repository and its two ids (`HEARTH_GITHUB_REPOSITORY`, `HEARTH_GITHUB_OWNER_ID`, `HEARTH_GITHUB_REPOSITORY_ID`) as GitHub gives them now: `env -u GH_REPO -u GH_HOST gh api 'repos/{owner}/{repo}' --jq '"HEARTH_GITHUB_REPOSITORY=\(.full_name)", "HEARTH_GITHUB_OWNER_ID=\(.owner.id)", "HEARTH_GITHUB_REPOSITORY_ID=\(.id)"'`, in a checkout of `main`, prints the three lines, which you paste into `infra/.env.local` as they are: the name it prints, not the one you typed, since GitHub may answer a former name of a renamed or transferred repository with the repository it now names, and the synth checks the subject only against these values. GitHub joins the claims with colons, each value after its key but `context`'s, whose value starts with its own word (`environment:` and the job's environment, for every deploy job), so the format is exactly `repo:{repository}:environment:{environment}:job_workflow_ref:{repository}/.github/workflows/deploy.yml@refs/heads/main`, with no `context:` label and no `ref:` claim. A repository GitHub names in its immutable form, as it does by default every repository created, renamed or transferred since mid-2026 (this one likely, C11-D55), has `{owner}@{ownerId}/{name}@{repositoryId}` in place of the first `{repository}`; GitHub doesn't say whether that form also reaches `job_workflow_ref`, so keep `{repository}` there. The synth refuses a format naming another repository, one not naming the deploy workflow on `main`, and any other shape (`subjectRepositoryProblem()` in `infra/src/config/env.ts`), but it takes either form of the repository in either place, so only the first `nonprod` run (step O.2, from C0.11 PR 4) proves which one GitHub sends, refused if it is wrong. A wrong one is corrected in `infra/.env.local`, and a reviewed PR records which form GitHub sends, the form alone and never a value, in TECH-SPEC T24 item 11 and `infra/.env.example`'s comment on `HEARTH_GITHUB_SUBJECT_FORMAT`: that PR is what the redeploys cite, since no PR holds `.env.local`. From a checkout of `main` at that PR, holding the corrected `.env.local`, `Hearth-Foundation` (whose RCP names the subjects) is deployed again under `HearthOrgAdmin` (step F), then both Baselines under `lz:pr-<that PR>` ([Reaching production: the break-glass role](break-glass.md)'s *A Baseline deploy under `lz:pr-N`*). Each diff changes the subjects alone: the deploy roles' trusts (`hearth-gh-deploy`, and in prod `hearth-gh-diff`) and, in Foundation, the RCP's `WebIdentityOnlyDeploySubjects`. Anything else stops that deploy. Once they have run, [the quarterly review](break-glass-review.md)'s step 6 reads the subjects as they stand, the second reviewer the trusts and an Owner the RCP: each must read `expected`. It takes either form of this repository, by the name and ids the `gh api` read above prints, and nothing else.

   A rename or transfer of the repository, or a rename of its owner, after the set-up changes its subject too: GitHub sends a renamed or transferred repository in its immutable form, which still carries the name, and a transfer changes the owner's id. Every trust then stops matching, and until the redeploys a subject in the `owner/name` form still names the path the repository left, which someone else may later take. An owner's rename frees that path to anyone at once, so before one, and only once no containment's `hearth-containment` is in place, an Owner cuts the GitHub roles off as a containment cuts off a role ([A security alert](security-alerts.md#containing-an-unexpected-session), step 5): a `hearth-containment` SCP on non-prod and prod alone, denying every action where `aws:PrincipalArn` is like `*:role/hearth-gh-*`, with no time condition, and, so that it can be seen to bind, every action where `aws:TokenIssueTime` is before a time a few minutes after its attachment and `aws:PrincipalArn` is like `*:role/aws-reserved/sso.amazonaws.com/*`. Organizations applies a policy only after a delay, and no person can make a `hearth-gh-*` session, so the rename waits until, in each of the two accounts, the person on call has seen a call refused before that time, as [a containment's step 4](security-alerts.md#containing-an-unexpected-session) checks before its cut-off, moving the time later if none is. Its policy id, that time, and when it was attached and when it was detached and deleted (or its statements removed), go in the on-call notes. It binds no session the redeploys use, and the Owner detaches it from both accounts and deletes it only once both Baselines have run and [the quarterly review](break-glass-review.md)'s step 6, read as for the correction, prints `expected` for the new trusts and the RCP. A containment needed meanwhile adds its statements to it ([A security alert](security-alerts.md#containing-an-unexpected-session), step 4); when the cut-off would end, the Owner instead removes its statements alone, and detaches the policy from a workload account that containment isn't in. So, on the day it happens, take the correction's path: a reviewed PR records that the name changed and, once a `nonprod` run has shown it, which form GitHub now sends, never a name or an id; the owner reads the name and ids again (the `gh api` read above), stops unless it prints the repository id `infra/.env.local` already holds, and the owner id too unless the repository was transferred (no rename or transfer changes a repository's id, while a path someone else has taken answers with theirs), and pastes the three lines into it; and from a checkout of `main` at that PR deploys `Hearth-Foundation` under `HearthOrgAdmin`, then both Baselines under `lz:pr-<that PR>`, each diff changing the subjects alone, read as for the correction. Until then create no repository at the path it left, and [the quarterly review](break-glass-review.md) finds the trusts and the RCP naming a former name. Rename or transfer the repository, or rename its owner, only this way.
3. The ops mailbox's address into `HEARTH_ALERT_EMAIL`, and C11-Q09's amounts into the five `HEARTH_BUDGET_*_USD`.

From C0.11 PR 4 this step also covers, in its own words: the GitHub environments and their secrets, the repository's Actions settings, the owner's narrowed GitHub token, and `.claude/settings.json`'s deny rules on any machine running Claude Code.

### F. The landing-zone shell, the synth and the asset check

Every deploy below runs these three parts, in this order, so no repository code runs where credentials exist.

1. In the credential-free shell, from `infra/` in the checkout: `HEARTH_TARGET=<target> AWS_EC2_METADATA_DISABLED=true npx cdk synth --app "node --env-file=.env.local bin/landing-zone.ts" --no-lookups`, with `<target>` one of `foundation`, `log-archive`, `nonprod-baseline` or `prod-baseline`. Its one line on standard error names the target; a refusal names a variable and what it must be, never its value.
2. Still there, the asset check, which runs no repository code: `jq -s -e 'map([(.files // {})[] | .source | select(has("executable"))] + [(.dockerImages // {})[]]) | flatten | length == 0' cdk.out/*.assets.json` must print `true`. Anything else (`false`, or an error because no manifest matched) stops the deploy.
3. In the credentialed shell, as the same operating-system user as part 1 (the CLI writes a read lock into `cdk.out`, *Before you start*), from its own folder, which holds no `cdk.json`, with the checkout's own CLI and the assembly's path (`CHECKOUT` is the checkout's path, as in step G): `"$CHECKOUT/node_modules/.bin/cdk" diff --app "$CHECKOUT/infra/cdk.out"`, read it whole, then `"$CHECKOUT/node_modules/.bin/cdk" deploy --app "$CHECKOUT/infra/cdk.out"`. Both read the synthesised assembly and run no repository code. Never run them from `infra/`: beside a `cdk.json` the CLI first runs any `build` command it names, with your credentials. Never use `npx` there, which outside the checkout would fetch the CLI from the registry, and never pass `--app` the entry itself.

**A first deploy failed.** A create that rolls back deletes what it made, the retained resources included (each is retained once made, `RetainExceptOnCreate`), with one exception: `Hearth-Foundation`'s `/hearth/security/org-trail` log group, under deletion protection, which CloudFormation can't delete, so its events name it `DELETE_SKIPPED`. In that stack's account, with the session that ran the deploy:

1. Read the stack's events (`aws cloudformation describe-stack-events --stack-name <the stack> --query 'StackEvents[].[LogicalResourceId,ResourceStatus,ResourceStatusReason]' --output text`), and fix the cause by a reviewed PR.
2. Turn termination protection off for that stack alone: `aws cloudformation update-termination-protection --no-enable-termination-protection --stack-name <the stack>`.
3. Remove each `DELETE_SKIPPED` leftover the events name (an exception *Don't* names). The trail's copy goes whether or not it holds events: the trail may have delivered for minutes before a later resource failed, and the copy only duplicates what the trail delivered to its bucket in log-archive, under Object Lock. First note, for the quarterly review, how many events it holds and over what times, counts and times only: Logs Insights on the group, in the console or with `aws logs start-query` and then `aws logs get-query-results`, with `stats count(*) as events, min(@timestamp) as first, max(@timestamp) as last`, so the reviewer can check that the trail bucket holds files for those times. Then `aws logs put-log-group-deletion-protection --log-group-identifier /hearth/security/org-trail --no-deletion-protection-enabled`, then `aws logs delete-log-group --log-group-name /hearth/security/org-trail`.
4. Run step F again from part 1: the CLI deletes the failed stack before it makes it anew, with termination protection on again.

First deploys run in the root (log-archive and the workload accounts through OAAR before their moves, management with `HearthSetUp`), where no `Workloads` fence binds. In a workload account already in `Workloads`, `HearthbaseStacksOnlyItsDeploy` lets only hearthbase's deploy role change a Baseline's termination protection, so a failed Baseline create there is cleared as tier 2. Note each step for the quarterly review.

### G. Bootstrapping an account

In the credentialed shell, from a folder with no `cdk.json` (beside one, the CLI would synthesise the app with your credentials), with the checkout's own CLI and the account read from the session, never typed:

```sh
ACCOUNT="$(aws sts get-caller-identity --query Account --output text)"
"$CHECKOUT/node_modules/.bin/cdk" bootstrap "$ACCOUNT/ap-southeast-1" \
  --qualifier hearthbase --toolkit-stack-name CDKToolkit-hearthbase \
  --template "$CHECKOUT/infra/bootstrap/hearth-bootstrap.yaml" \
  --termination-protection --public-access-block-configuration true --no-notices
```

`CHECKOUT` is the checkout's path. Management and log-archive take `hearthbase` alone. The workload accounts also take `hearthapp`, once their Baseline has made `hearth-boundary` (step L): `--qualifier hearthapp --toolkit-stack-name CDKToolkit-hearthapp --custom-permissions-boundary hearth-boundary`, the rest the same. Each qualifier has its own toolkit stack, so the second never replaces the first. Never pass `--cloudformation-execution-policies`. Every account is bootstrapped from this committed template, whose deploy and file-publishing roles' trust takes a break-glass session's source identity, which an `lz:pr-` deploy needs (TECH-SPEC T24 item 11); an account bootstrapped from an older template is bootstrapped again from the committed one before step J or L moves it. Once an account sits in its OU, a bootstrap upgrade is tier 2 (step Q).

### H. The set-up permission set

Management has no OAAR, and `HearthOrgAdmin` is made by `Hearth-Foundation` itself, so the first deploys need a permission set of their own.

1. Synthesise `foundation` (step F, part 1 alone) and read `HearthOrgAdmin`'s inline policy from `cdk.out/Hearth-Foundation.template.json` (the `AWS::SSO::PermissionSet` named `HearthOrgAdmin`, its `InlinePolicy`).
2. As the root user, make `HearthSetUp` in Identity Center: AdministratorAccess, a 1-hour session, and that inline policy pasted whole, so it carries both `NoModels` and `NoAccountRemoval`. Assign it to the owner in management alone.
3. Sign in with `HearthSetUp`, and put the root user's keys away. `HearthSetUp` runs management's bootstrap, log-archive's first deploy through OAAR and `Hearth-Foundation`'s first deploy; step K deletes it.

### I. Trusted access, Cost Explorer and the anomaly monitor

1. Enable trusted access for CloudTrail, GuardDuty, IAM Access Analyzer and Identity Center.
2. Enable Cost Explorer.
3. Look for a cost anomaly monitor AWS may already have made: `aws ce get-anomaly-monitors --query 'AnomalyMonitors[].[MonitorName,MonitorType,MonitorDimension]' --output text`. If one watches AWS services by dimension, delete it (`aws ce delete-anomaly-monitor`) before Foundation's first deploy, which makes its own and would otherwise fail.

### J. Log-archive, through OAAR while it sits in the root

Log-archive comes before Foundation: the trail Foundation makes needs its bucket and its `hearth-sec` key.

1. Through OAAR in log-archive (from `HearthSetUp` in management): account-level Block Public Access on, and EBS encryption by default on, in the console or with `aws s3control put-public-access-block --account-id "$ACCOUNT" --region ap-southeast-1 --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true` and `aws ec2 enable-ebs-encryption-by-default --region ap-southeast-1`, the account's id read from the session, never typed (`ACCOUNT="$(aws sts get-caller-identity --query Account --output text)"`).
2. Bootstrap `hearthbase` (step G).
3. From management, make log-archive the delegated administrator of GuardDuty, in ap-southeast-1 and in us-east-1, and of IAM Access Analyzer.
4. Deploy `Hearth-LogArchive` (step F, target `log-archive`).
5. Through OAAR in log-archive, in both Regions: GuardDuty's organisation configuration auto-enables `ALL` accounts, with the foundational sources and S3 Protection; Runtime Monitoring stays off.
6. Through OAAR in log-archive: confirm its topic's subscription (step N), and read back what nobody can read there once it sits in `Security` (*Check it worked*, "In log-archive"): GuardDuty's organisation configuration in both Regions, `CDKToolkit-hearthbase` and its roles, and the archive bucket's Object Lock configuration; and step 1's two settings, which only tier 2 can set once it has moved.
7. Move log-archive into `Security`. From then on nobody administers it, its own break-glass role included; `Hearth-LogArchive` changes only as tier 2 (step Q). Steps 1, 3, 5 and 6 can't be done after this move.

### K. Foundation, in management

1. Confirm the billing set's managed policy: `aws iam list-policies --scope AWS --query "Policies[?PolicyName=='AWSBillingReadOnlyAccess'].PolicyName" --output text` prints its name. If it prints nothing, stop: the set's policy name is wrong, and a PR fixes `infra/src/foundation/identity-center.ts` first.
2. Bootstrap `hearthbase` in management (step G), with `HearthSetUp`.
3. Deploy `Hearth-Foundation` (step F, target `foundation`), with `HearthSetUp`. It attaches the guardrails, makes the five permission sets and their assignments, the trail and its copy, the assured alarms and the copy's intake alarm, the budgets and management's topic. The intake alarm may sit in ALARM until the copy's first events land, minutes after the trail is made. Provisioning the sets makes Identity Center's own SAML provider in log-archive, non-prod and prod, and A6 may alarm on it once its filters exist: that is Identity Center's own shape, which [A security alert](security-alerts.md)'s A6 row tells apart from a person's. Note it for the first quarterly review, as step 6 notes A4.
4. Sign in with `HearthOrgAdmin` and confirm it works.
5. With `HearthOrgAdmin`, confirm management's topic's subscription (step N).
6. Unassign `HearthSetUp` and delete it. A4 alarms: note it as the first entry for the quarterly review.

Later deploys of `Hearth-Foundation`, after a reviewed PR, are the same step F under `HearthOrgAdmin` (A3 alarms on each session).

### L. Each workload account, non-prod then prod, through OAAR while it sits in the root

For non-prod first, then prod:

1. Through OAAR: account-level Block Public Access on, and EBS encryption by default on, in the console or with step J.1's two commands, each naming ap-southeast-1.
2. Bootstrap `hearthbase` (step G).
3. Deploy its Baseline (step F, target `nonprod-baseline` or `prod-baseline`). It makes GitHub's OIDC provider and roles, `hearth-break-glass`, `hearth-boundary`, the fast alarms, the topic, the image repository, the zones and the parameters.
4. Bootstrap `hearthapp` with `--custom-permissions-boundary hearth-boundary` (step G).
5. Read back the S3 prefix list: `aws ec2 describe-managed-prefix-lists --filters Name=prefix-list-name,Values=com.amazonaws.ap-southeast-1.s3 --query 'PrefixLists[].PrefixListId' --output text` prints the id `infra/src/config/profiles.ts` holds. A different id stops here, for a reviewed PR to the profile.
6. Through OAAR: confirm its topic's subscription (step N), and read back what nobody can read there once it sits in `Workloads` (*Check it worked*, "In each workload account"): both bootstrap stacks and their roles, the image registry's scanning configuration, and step 1's two settings, which only tier 2 can set once it has moved. Then read each zone's name servers: the zone's id from SSM (`aws ssm get-parameter --name /hearth/<env>/zone/app --query Parameter.Value --output text`, then `/hearth/<env>/zone/usercontent`, `<env>` being `nonprod` or `prod`), then `aws route53 get-hosted-zone --id <the zone's id> --query 'DelegationSet.NameServers'`. For non-prod, read them a second way too, from its Baseline's outputs (`aws cloudformation describe-stacks --stack-name Hearth-nonprod-Baseline --query 'Stacks[0].Outputs'`, `AppNameServers` and `UserContentNameServers`), for the delegation of `nonprod.` below; prod's are for step M. Write them down; name servers are public, not secret.
7. Move the account into `Workloads`. From then on its Baseline changes only under break-glass with an `lz:pr-` reason ([Reaching production: the break-glass role](break-glass.md)), and a bootstrap upgrade only as tier 2. Step 6 can't be done after this move, but for its read-backs in non-prod, which `HearthNonprodOperator` makes while it is assigned. Prod moves only once step P.1's non-prod run and step P.4 have proved, in non-prod, the chain an `lz:pr-` session takes into hearthbase: if it fails there (an older bootstrap, say), prod's fix is still a plain OAAR step rather than tier 2.

Between non-prod and prod, the delegation of `nonprod.`:

1. Take non-prod's two readings from step L.6, made through OAAR before non-prod moved into `Workloads` (OAAR is refused there since): its Baseline's outputs and each zone. The two must agree.
2. Put them into `NONPROD_NAME_SERVERS` in `infra/src/config/profiles.ts` by a reviewed PR, which the owner reads before it merges (an owner's-read value). The same PR regenerates the inventory snapshot (`CI= npx vitest run infra/src/inventory.test.ts -u`), and the person reads its change: prod's `AWS::Route53::RecordSet` goes from 2 to 4. The Baseline tests follow the committed name servers, so none turns red.
3. Before prod's Baseline deploys, compare the committed lists, from a fresh checkout of `main`, with the L.6 readings, and with both read again in non-prod by someone in the non-prod operators group, with `HearthNonprodOperator` (read-only, and the one set that reads non-prod's zones and stacks once it sits in `Workloads`), the same two ways as L.6. Refuse any difference: a wrong name server would hand someone else a subdomain of prod's domain.

### M. The domains at the registrar

Point each registrable domain, at the registrar, at the name servers step L read for prod's zones before prod moved into `Workloads` (no identity reads prod's zones after that move), and turn on registry lock where the registrar offers it.

### N. Confirm each email subscription

Each of the four `hearth-ops-alerts` topics emails the ops mailbox a confirmation when its stack first deploys: log-archive's in step J, management's in step K, non-prod's and prod's in step L. Each is confirmed in that account's own step, within two days of the deploy (the confirmation's token expires) and before the account moves into its OU, since it needs that account's own credentials: OAAR in a member account, `HearthOrgAdmin` in management.

Ask for the ops mailbox's link scanning (a mail service's safe-links or preview fetches) to be off for AWS's notification address, since a scanner that follows the link confirms the subscription unauthenticated. Never confirm one by opening the email's link. A subscription confirmed by its link takes an unsubscribe from anyone holding any later alert email, by the unsigned link at its foot, which no guardrail can refuse; one confirmed with a signed call refuses every unsubscribe that isn't signed by its account, and CloudFormation can't ask for that itself.

1. Copy the confirmation link from the email without opening it (and with nothing previewing it), and take its `Token` parameter's value.

One whose subject isn't this repository's is an incident ([A security alert](security-alerts.md)). A10 emails once for each new finding, the GitHub roles' and Identity Center's: expected here, and triaged as the A10 row says.
  - Once `Hearth-LogArchive` has deployed, the analyzer's active findings on keys: `aws accessanalyzer list-findings-v2 --analyzer-arn <the analyzer> --filter '{"resourceType":{"eq":["AWS::KMS::Key"]},"status":{"eq":["ACTIVE"]}}' --query 'findings[].[resource,error]' --output text`, where `aws accessanalyzer list-analyzers --type ORGANIZATION --query 'analyzers[].arn' --output text` prints the analyzer, `hearth-org-external`. None stands on `hearth-sec` or `hearth-archive`, and none carries an `error` (the analyzer couldn't read the key, which is a fault in its policy, fixed by PR).

### The quarterly read-backs

Each quarter, read back again everything listed for management (with `HearthOrgAdmin`), the two buckets the reviewer reads, and non-prod's list with `HearthNonprodOperator` while it is assigned. The rest of log-archive's and the workload accounts' lists can be read there only as tier 2, so instead the second reviewer or an Owner runs this query on `/hearth/security/org-trail` in management over the quarter. It lists any change to those since steps J and L read them (the topic's by every field A6 (d) reads, `resourceArn` included, which is how a data protection policy or a tag change names it); none is expected, and each one is explained by a recorded tier-2 change or a reviewed Baseline deploy under its `lz:pr-` reason, or is a finding for [the quarterly review](break-glass-review.md):

```
fields @timestamp, recipientAccountId, eventSource, eventName, errorCode
| filter eventName not like /^(Get|List|Describe)/
| filter (eventSource = "guardduty.amazonaws.com" and eventName like /OrganizationConfiguration/) or eventName = "PutRegistryScanningConfiguration" or eventName = "PutObjectLockConfiguration" or (eventSource = "iam.amazonaws.com" and requestParameters.roleName like /^cdk-hearth/) or (eventSource = "cloudformation.amazonaws.com" and requestParameters.stackName like /CDKToolkit-hearth/) or (eventSource = "sns.amazonaws.com" and (requestParameters.topicArn like /:hearth-ops-alerts$/ or requestParameters.subscriptionArn like /:hearth-ops-alerts:/ or requestParameters.resourceArn like /:hearth-ops-alerts$/ or requestParameters.name = "hearth-ops-alerts")) or (eventSource = "monitoring.amazonaws.com" and eventName like /AlarmMuteRule|AlarmActions/) or eventName like /AccountPublicAccessBlock|^(Put|Delete)PublicAccessBlock$|EbsEncryptionByDefault|EbsDefaultKmsKeyId/
| sort @timestamp desc
```

Its monitoring clause lists management's own alarm writes too, a mute rule made or deleted and actions turned off or on, which a read-back of the alarms' state can't see once they are undone; none is expected. Its last clause lists any change to steps J.1's and L.1's two settings, the account's public access block and EBS encryption by default, with its default key: none is expected after those steps. Their names in the trail are unproved until the set-up's own calls show them: once step K.3's trail delivers, run the query over step L.1's time in each workload account (J.1 comes before the trail), and it must list the public access block's put and `EnableEbsEncryptionByDefault`; if either is missing, find its event in the copy by account and time, and correct the clause by a reviewed PR with its name.

## Closing a Hearth account

Closing a Hearth account, or taking it out of the organisation, would lift every SCP from it, the evidence floor included, and end its content after AWS's post-closure period. `HearthOrgAdmin`'s own sessions are refused both calls (`NoAccountRemoval`). That guards against a slip; it is not a fence, since a role a session makes in management isn't held by it, and A5 alarms on either call whoever makes it. It is a task for the management root's keys alone, after a reviewed decision, and the DPO and the second reviewer are told before it is done.

## Don't

- Run `cdk bootstrap`, `cdk diff` or `cdk deploy` from `infra/` (or any folder holding a `cdk.json`), or with `--app` naming the entry, or synthesise in a credentialed shell: each runs repository code under credentials.
- Edit an SCP, the RCP, a permission set, a topic, a rule or an alarm in the console. Every change is a reviewed PR, with five exceptions: step H's making of `HearthSetUp`, and step K's unassigning and deleting it; step N's confirmation or replacement of a subscription; a security alert's containment ([A security alert](security-alerts.md#containing-an-unexpected-session)); step E.2's cut-off of the GitHub roles before an owner's rename (a `hearth-containment` SCP); and step F's *A first deploy failed*, which turns one failed stack's termination protection off and removes what its rolled-back create left, nothing else.
- Open the link in a subscription's confirmation email, or the unsubscribe link in any alert email.
- Use `CfnAccount` or Control Tower.
- Add an SMS subscription to any topic.
- Paste an account id, an ARN, a `.env.local` line or a command's output into a chat, an issue, a PR or a coding agent's session.
- Let a coding agent run any step.
